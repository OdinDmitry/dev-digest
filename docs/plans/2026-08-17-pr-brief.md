# Development Plan: PR Brief

Spec: docs/specs/cross/SPEC-02-pr-brief.md
Date: 2026-08-17
Execution mode: multi-agent (2 tracks + a frozen Step 0 + an Integration track)

Design refs: `docs/specs/cross/_design/SPEC-02-pr-brief/1.png` … `7.png`.

## Goal

Put a short, cached synthesis of what a pull request changes and why above
everything else on its Overview view, next to the most recent run's verdict,
finding/blocker counts and PR score; add a risk-areas subsection to the
existing intent card and an ordered "review focus" section below it, both
anchored in files the change actually touches and both navigable into the
Files-changed view. The synthesis comes from exactly one model call per head
commit, over inputs that never include a diff hunk body, and is cached against
the pull request's head commit SHA.

## Out of scope

- Per-brief cost/token accounting. The `$0.014  8.2K→1.3K` line in mockups 1
  and 2 is **not rendered at all** — no element occupies that space.
- Any change to how agent runs, findings, verdicts or scores are produced. This
  feature reads them.
- A second model call of any kind (review, validation, scoring of the brief).
- Repository/issue-tracker search for a related issue; indexing, chunking,
  embedding or searching for specs.
- Invalidating a brief when intent, blast radius or an agent run changes.
- Editing, annotating, dismissing or commenting on a brief, a risk or a
  review-focus item.
- Adding a new PR-detail tab, a new route, or a new nav item.
- Reworking SPEC-01's project-context browse/attach UI, its token counter, or
  its scan layer. This plan consumes them
  (`docs/plans/2026-08-16-project-context-browse-attach.md`,
  `docs/plans/2026-08-16-project-context-run-injection.md`).
- Repurposing, renaming or deleting the legacy `PrBrief` / `Risk` / `Risks` /
  `BlastRadius` shapes in `contracts/brief.ts`. They stay as they are (dead
  scaffolding), for the reason `contracts/blast.ts:3-16` already records.
- Adding a new `FeatureModelId`. `risk_brief` already exists and is unused.

## Shared contract (frozen before tracks fork)

Written once into `server/src/vendor/shared/contracts/brief.ts`, appended
below the existing content (nothing above it changes), then copied verbatim
into the client's file. `RiskSeverity` (`brief.ts:47`) is **reused** for both
the per-risk severity and the whole-change risk level — the spec defines them
as the same three ordered levels.

```ts
// ---- SPEC-02: the generated PR brief ----------------------------------

/** A reference the brief may point at. `path` is repository-relative and MUST
 *  be present in the pull request's changed files (grounded server-side).
 *  `endpoint`, when non-null, is an endpoint from the blast radius. */
export const BriefFileRef = z.object({
  path: z.string(),
  start_line: z.number().int().nullable().default(null),
  end_line: z.number().int().nullable().default(null),
  endpoint: z.string().nullable().default(null),
});
export type BriefFileRef = z.infer<typeof BriefFileRef>;

export const BriefRisk = z.object({
  kind: z.string(),
  title: z.string(),
  explanation: z.string(),
  severity: RiskSeverity,
  refs: z.array(BriefFileRef).min(1),
});
export type BriefRisk = z.infer<typeof BriefRisk>;

export const BriefFocusItem = z.object({
  refs: z.array(BriefFileRef).min(1),
  reason: z.string(),
});
export type BriefFocusItem = z.infer<typeof BriefFocusItem>;

/** The stored document (`pr_brief.json`). Replaced whole, never patched. */
export const BriefDoc = z.object({
  what: z.string(),
  why: z.string(),
  risk_level: RiskSeverity,
  risks: z.array(BriefRisk),
  review_focus: z.array(BriefFocusItem),
});
export type BriefDoc = z.infer<typeof BriefDoc>;

/** The stored document plus the identity it was produced for. */
export const BriefRecord = BriefDoc.extend({
  pr_id: z.string(),
  head_sha: z.string(),
});
export type BriefRecord = z.infer<typeof BriefRecord>;

/** `ready` — `brief` is present and matches the PR's current head commit.
 *  `absent` — nothing stored for this head commit; the client starts one
 *  generation. `unavailable` — this generation cannot produce a brief
 *  (input over budget after every optional drop, AC-18). */
export const BriefStatus = z.enum(['ready', 'absent', 'unavailable']);
export type BriefStatus = z.infer<typeof BriefStatus>;

export const BriefEnvelope = z.object({
  status: BriefStatus,
  brief: BriefRecord.nullable(),
  /**
   * Machine-readable cause when `status === 'unavailable'`, else null.
   * Exactly two values are produced: `'intent_absent'` (no persisted intent
   * yet — retryable, nothing stored, T17) and `'input_budget'` (over budget
   * with every optional input already dropped, T13/T17). Both mean "no model
   * call was made". Kept as a plain string, not an enum, so adding a cause
   * later is not a breaking contract change.
   */
  reason: z.string().nullable(),
});
export type BriefEnvelope = z.infer<typeof BriefEnvelope>;

/** The most recent completed review on a pull request, as one unit — either
 *  all four values or `null` for the whole object (AC-5). NOT `RunSummary`:
 *  that name is taken by contracts/trace.ts. */
export const PrRunSummary = z.object({
  verdict: z.string(),
  findings_count: z.number().int(),
  blockers_count: z.number().int(),
  score: z.number().int().nullable(),
});
export type PrRunSummary = z.infer<typeof PrRunSummary>;
```

## Placement decisions

  quick table — "Prompt assembly, grounding, diff reasoning → ring 0,

## Open questions / assumptions

1. **Execution mode was not specified and could not be asked.** Assumed
   **multi-agent, 2 tracks**, because with the contract and the schema frozen in
   Step 0 the server and client file lists are fully disjoint and each side's
   tests are hermetic (the client mocks `@/lib/api`). If the orchestrator
   prefers a single pass, the plan reads top-to-bottom unchanged — collapse the
   track headings and keep the order.
2. **"The blast radius summary" does not exist as a produced value.**
   `PrBlastRadius` (`contracts/blast.ts:48-72`) has no `summary`; the field the
   spec's provenance table points at belongs to the never-built legacy
   `BlastRadius` (`contracts/brief.ts:39-44`). Assumed: the summary is composed
   deterministically from `PrBlastRadius` by `blastSummaryLine` (T12), with no
   model call and no recomputation of the blast radius itself.
3. **"The project-context documents attached for that generation" has no
   defined owner.** SPEC-01 attaches documents to an agent or a skill only
   (`contracts/context.ts:44-45`), and a brief generation is neither.
   **Decided by the user (2026-08-18):** the documents are the ones the agents
   reviewing this pull request carry — directly and through their skills. T16
   therefore unions `assembleForAgent` over the workspace's **enabled** agents,
   in `name ASC, id ASC` order, de-duplicated by path. Two consequences follow
   and are intended: a document attached to a skill no agent uses never reaches
   a brief (SPEC-01 line 318), and a disabled agent's attachments are excluded
   — narrower than SPEC-01's usage count, which deliberately counts disabled
   owners, because that count answers "who carries this document" while the
   brief asks "what context reviews this PR". The per-agent order inside each
   agent's set stays SPEC-01's (skill-inherited first, AC-13), which is what
   gives AC-17's "last in attached order first" a well-defined meaning.
4. **"The most recent completed agent run" is read as "the most recent
   completed review".** AC-4 requires the card's score to equal the list's, and
   the list's score is the newest `reviews` row of `kind: 'review'`
   (`pulls/routes.ts:145-148,234`), which is what a completed run produces. Some
   reviews carry no `run_id` at all — the seeded one does
   (`seed.ts:151-164`) — so reading `agent_runs` directly would make AC-3/AC-4
   unobservable on the only data the e2e suite may touch. Assumed: verdict and
   score come from that review row, finding and blocker counts from its
   undismissed findings via the existing `rollupSeverities` (blockers = the
   CRITICAL count). T15 makes the equality structural rather than coincidental.
5. **AC-19's endpoint half needs a representable form.** The spec's Contracts
   section defines only a *file* reference, yet AC-19 also speaks of an
   endpoint. Assumed: `BriefFileRef` carries an optional `endpoint` alongside
   its `path`; a reference is dropped when its path is not in the changed files
   **or** when its endpoint is not in the blast radius' endpoint set. Both
   halves are then real, exercised code paths with their own tests, and the
   Contracts sentence "a risk carries at least one file reference" stays true.
   Had the endpoint been left unrepresentable, AC-19 would have been half
   vacuous — a binding that cannot fail.
6. **AC-2 is a post-condition, and only one model call is permitted.** So it
   cannot be met by retrying. Assumed: the prompt asks for it, and
   `enforceNotTitle` (T8) guarantees it by substituting a deterministic
   fallback built from the change statistics when the model returns the title.
   This is the only place in the feature where the stored text is not the
   model's own words; it fires rarely and is unit-tested directly.
7. **Generation is synchronous, mirroring L03.** AC-7's "generating" state is
   the pending POST, exactly as `IntentCard` renders "Deriving intent…" today
   (`IntentCard.tsx:77-84`). No job queue, no polling endpoint. If a future
   requirement needs the brief to survive a page reload mid-generation, that is
   a job-backed redesign and is out of scope here.
8. **The e2e suite depends on T20.** Without a seeded `pr_brief` row for PR
   #482, every flow that lands on that PR's Overview tab (02, 04, 05 and the
   new 12) fires a real generation. Treat T20 as a correctness task, not a
   convenience one.
