- _2026-08-17_ — **Project Context listing meets its 2 s / 2 000-file budget with no persisted token cache — measured cold 1,347 ms, warm 466 ms** — measured by mirroring `ContextService.listDocuments`' hot path (`listMarkdown` → `PQueue(READ_CONCURRENCY=16)` of `readDocument` + `TiktokenTokenizer.count` → sort) over a throwaway tree of 2,000 `.md` files across 5 folders, ~1–8 KB each, 722,748 tokens total. "Cold" is a fresh process, where the `${repoId}:${path}:${size}:${mtime}` memo in `service.ts` is empty and every file is read AND BPE-encoded; "warm" is a second pass in the same process, where every file is still re-read but every token count is a memo hit. Cold was the case the plan flagged as at risk and pre-scoped a `context_documents` cache table for — **that follow-up is not needed at this limit on this hardware**, and the ~2.9× cold/warm gap shows BPE encoding, not file I/O, is what the memo removes. Re-measure before raising `DISCOVERY_LIMIT` (2,000) or `MAX_DOCUMENT_BYTES` (256 KB); a corpus of larger documents will move cold much more than warm. An earlier verification pass recorded ~830 ms warm on a different corpus — both are well inside budget, so treat either as an order-of-magnitude fact, not a regression baseline.
- _2026-08-16_ — **Fixed the `readDocument` symlink/junction escape (see Open Questions 2026-08-16) with a second `realpath()`-based containment check, keeping the existing string-prefix check as a cheap fast path** — `modules/context/scan.ts`'s `readDocument` now does `[realRoot, realTarget] = await Promise.all([realpath(rootResolved), realpath(target)])` after the fast-path string check passes, then re-checks `realTarget` starts with `realRoot + sep` before ever calling `stat`/`readFile`. `realpath()` resolves symlinks AND win32 junctions along the whole path, so a junction created inside the working copy pointing outside it now correctly fails the second check and returns `null` (previously it silently followed through). `realpath()` on a nonexistent path throws — caught and treated as `null`, consistent with the function's "never throw" contract. Confirmed against `test/context-scan.test.ts`'s junction repro (previously red, now green) and the full existing suite (188/188 unit tests, no regression).

## Codebase Patterns

- _2026-08-22_ — **A row-type leak that keeps moving between two ring-2 files on successive review rounds is a sign the fix belongs one ring OUTWARD, in the repository, not in either ring-2 file.** `modules/eval/runner.ts` needed an `AgentRow`-narrowed `EvalAgentConfig` in two places: `service.ts`'s `startRun()` (which already had a resolved agent) and `runner.ts`'s own `verifyCase(workspaceId, caseId)` (whose frozen AC-46 signature takes no agent, so it resolves its own via `AgentsRepository.getById`, which returns a raw `AgentRow`). Round 1 put the narrowing function `toEvalAgentConfig` in `runner.ts` and had `service.ts` import it — flagged, because `runner.ts` is ring 2 and held both the row-consuming function's definition and its one `AgentRow`-typed call site. Round 2 "fixed" it by keeping `EvalAgentConfig` in `runner.ts` but narrowing at the `verifyCase` call site instead — same file, same violation, just moved a few lines down. The actual fix: give `AgentsRepository` (ring 3, `modules/agents/repository.ts`) a `getConfigById(workspaceId, id)` method that calls `getById` and maps through a new `toAgentConfig`/`AgentConfig` pair in `modules/agents/helpers.ts` — `AgentRow` now dies inside `modules/agents/`, before it ever reaches `modules/eval/`. `runner.ts` keeps its own `EvalAgentConfig` interface declaration (structurally identical to `agents/helpers.ts`'s `AgentConfig`, no import between the two modules needed — TypeScript's structural typing makes the repository's return value assignable to `EvalAgentConfig`-typed parameters without either module naming the other's type). Generalizable rule: if a plan or review keeps re-flagging "row type in ring 2" and the fix keeps relocating it between a service and a sibling ring-2 file, stop moving it sideways — add (or extend) a repository method that returns the already-narrowed shape instead.

- _2026-08-17_ — **`ContextService.assembleForRun` (the run-time resolver, `docs/plans/2026-08-16-project-context-run-injection.md` U5) deliberately does NOT write into the private `tokenCache` Map that `listDocuments`/`countTokens` use** — that cache is keyed `${repoId}:${path}:${sizeBytes}:${mtimeMs}`, and the size/mtime come from the directory-walk `stat` that `listMarkdown` already did; `assembleForRun` only has `readDocument`'s return (text, no stat metadata), and adding a second fs.stat call per document to build a compatible key would mean touching `scan.ts` (out of this task's file scope: only `helpers.ts`/`service.ts`). It counts each survivor directly via `this.deps.tokenizer.count(text)` instead — the same "count directly, no cache" choice the class's own doc comment already documents for `getDocumentText`/`getOwnerAttachments`, both bounded by attachment count rather than the 2,000-file NFR. If a future change makes `assembleForRun` a hot path (called far more often than once per run) and this becomes measurably expensive, revisit by extending `scan.ts`'s `readDocument` (or adding a stat-returning sibling) rather than inventing a second, differently-keyed cache.

Any future `ContextService` method that needs to confirm a skill belongs to the workspace has to do it in `routes.ts`, not by adding a skills dep to the service.
- _2026-08-07_ — **A plan's literal `grep -rn "X" path/` static guard matches doc comments too, not just imports — phrase compliance-explaining prose to avoid the banned substring** — implementing `specs/0005-blast-radius.md` (blast module), writing `blast/service.ts`'s header comment as "Zero Drizzle, zero `db/schema` imports, zero `Container`" made the plan's own verification commands (`grep -rn "drizzle\|db/schema" server/src/modules/blast/`, `grep -rn "Container" server/src/modules/blast/service.ts`) print a hit — on the comment itself, not an actual import. grep has no concept of "this is prose explaining an absence" vs "this is the thing being grepped for". - _2026-08-07_ — **`RepoIntelRepository.getFileRankFor` returns `{ path, percentile }`, NOT `{ path, rank }`** — despite `repo-intel/service.ts` and plan prose elsewhere casually saying "sort by `file_rank.rank`", the one repository method that reads `file_rank` for a specific path set (`getFileRankFor`, used by blast's `reverseImportClosure` overflow-ranking per `specs/0005-blast-radius.md` §4) only ever selects `percentile`, not the raw `rank` column — `getRankedPaths` is the only method that selects `rank` (and it takes no path filter, just a `LIMIT`). `percentile` is monotonic with `rank` (both derived from the same PageRank score in `pipeline/rank.ts`), so sorting by `percentile DESC` produces an identical relative order to `rank DESC` for the purpose of "keep the highest-ranked files on overflow" — but a future reader expecting a literal `.rank` field off `getFileRankFor`'s return type will not find one. - _2026-08-07_ — **`waitForPrRuns` (`test/helpers/runs.ts`) now THROWS on timeout instead of returning whatever it has** — it previously did `if (Date.now() - start > timeoutMs) return runs;`, so a run that never reached a terminal status surfaced three frames later as `TypeError: Cannot read properties of undefined (reading 'findings')` on `reviews[0].findings[0].id` — an error that points at the review assertion and says nothing about the actual cause (a slow pre-review step, see Recurring Errors & Fixes 2026-08-07). ## Tool & Library Notes

- _2026-08-22_ — **`pnpm typecheck` (`tsc --noEmit -p tsconfig.json`) does NOT cover `test/**` — `tsconfig.json`'s `include` is `["src/**/*.ts"]` only, and vitest itself doesn't typecheck (esbuild transpile-only), so a test-side stub object that no longer structurally satisfies an interface (e.g. a hand-rolled `EvalRepository` stub cast `as unknown as EvalRepository` missing a newly-added method like `writeLatestResult`) compiles clean and only fails at RUNTIME — as a `TypeError: repo.<method> is not a function` inside whatever try/catch happens to wrap the call site, often reported as a misleading downstream symptom (here: every `EvalRunner.execute()` test looked like it was reporting `status: 'failed'`/every case erroring, not "a stub is missing a method"). Confirmed while writing `server/test/eval-runner.test.ts`'s D26 tests: `runner.ts`'s `execute()` started calling `repo.writeLatestResult(...)` per case (SPEC-04 delta), and every existing test in that file that starts a run failed after case 1 until the stub got the method added back — `pnpm typecheck` was clean throughout, so it gave no warning. When a repository/service interface a test double implements gains a new method, grep the test file's `Pick<...>`/stub object literal directly rather than trusting `pnpm typecheck` to catch the gap — it won't.
- _2026-08-21_ — **`db.selectDistinctOn([col], fields)` (drizzle-orm 0.38, pg-core) is the right primitive for "one row per group, the newest by some order" — no window function needed.** Used in `EvalRepository.latestRunPerAgent` (SPEC-04 delta, D5) to get each agent's most-recent `eval_suite_runs` row of ANY status in one query: `db.selectDistinctOn([t.evalSuiteRuns.agentId], SUITE_RUN_SELECT).from(...).orderBy(asc(agentId), desc(startedAt), desc(id))`. Postgres requires the `ORDER BY` to start with the `DISTINCT ON` expression(s) — `asc(t.evalSuiteRuns.agentId)` must be the first `orderBy` argument, with the tie-break columns after it; get that order wrong and Postgres throws `SELECT DISTINCT ON expressions must match initial ORDER BY expressions`, not a silent wrong-row bug.
- _2026-08-21_ — **On this Windows box, Docker Desktop is not left running between sessions — `docker ps` fails with `ECONNREFUSED`/`dockerDesktopLinuxEngine` pipe-not-found even though the `devdigest-postgres` container and its named volume both still exist.** Launching `"/c/Program Files/Docker/Docker/Docker Desktop.exe"` in the background and polling `docker ps` (checked every few seconds, up to ~2 min) is enough — Docker Desktop auto-starts its existing containers that have a restart policy, so `devdigest-postgres` came back up on its own once the daemon was reachable; only needed to wait for its healthcheck (`docker inspect -f '{{.State.Health.Status}}' devdigest-postgres` → `healthy`) before `pnpm db:migrate`/`pnpm db:seed` would connect. Needed for the SPEC-04 delta plan's D4 (`pnpm db:generate && pnpm db:migrate`) — don't conclude Postgres is unreachable/misconfigured from a bare `ECONNREFUSED` on this box without first checking `docker ps`.
- _2026-08-21_ — **`postgres` (the postgres-js driver behind `drizzle-orm/postgres-js`) throws errors carrying `.code` = the raw Postgres SQLSTATE — `'23505'` for a unique-violation — so that's the field to check when translating a DB constraint into an HTTP status, no wrapper/parsing needed.** No prior instance of this in the codebase (`grep -rn "23505\|unique_violation" server/src` was empty before this). Used in `modules/eval/runner.ts`'s `isUniqueViolation()` to translate the `eval_one_running_per_agent` partial unique index's violation into a 409 (AC-16 — two concurrent `POST /agents/:id/eval-runs` for the same agent can't both win). The check is a plain `(err as { code?: string }).code === '23505'`; `instanceof postgres.PostgresError` also works but isn't needed for this one code.
- _2026-08-05_ — **Node's built-in `net.BlockList` (Node 15+) is the right primitive for an SSRF address allowlist/denylist — don't hand-roll CIDR math** — `adapters/webfetch/https.ts`'s `isBlockedAddress()` builds one `BlockList` with `addSubnet`/`addAddress` calls for the private/loopback/link-local/CGNAT/multicast ranges, IPv4 and IPv6 both, and `blockList.check(ip, family)` handles IPv4-mapped IPv6 literals (`::ffff:10.0.0.5`) correctly against the IPv4 rules without any extra unwrapping code. `node:net`'s `isIPv4`/`isIPv6` are enough to pick the family to pass to `check()`. No new dependency needed.
- _2026-08-04_ — **`drizzle-kit generate` hangs forever on stdin from this sandboxed Bash tool whenever a schema diff both removes and adds columns on the same table** — it prompts an interactive arrow-key "created or renamed from X?" question per new column when a same-table diff has any removed columns to match against, and neither `printf '\n'` nor `yes ""` piped into it resolves the prompt here (the TUI reads raw keypresses, not lines, so a non-TTY stdin just hangs rather than being consumed). Confirmed by killing the process and retrying. Workaround: split the schema edit into two separate `db:generate` passes — first commit ONLY the column removal (produces a clean `DROP COLUMN` migration, no prompt, since nothing new exists yet to rename FROM), then edit again to add the new columns (clean `ADD COLUMN` migration, no prompt, since nothing was removed in that diff). Used successfully for the `conventions` table's `accepted:boolean` → `status:enum` + evidence-line-numbers change (migrations `0013`/`0014`).
- _2026-08-04_ — **fflate's `unzipSync({ filter })` runs against the central directory BEFORE decompression, which is exactly where an "untrusted archive" policy belongs** — the filter callback receives `{ name, size, originalSize, compression }` and returning `false` means those bytes are never inflated at all, so `modules/skills/import.ts` can promise that executable archive members are not merely ignored but never read. Two caveats: `originalSize` comes from the zip header and is attacker-controlled, so the decompressed length must be re-checked afterwards (and a running total kept across members); and fflate's `zipSync({ mtime })` rejects the epoch with `Error: date not in range 1980-2099` — the zip timestamp format starts at 1980, so a "fixed timestamp for reproducible archives" must be an in-range date, not `0` (bit `scripts/build-skill-fixture.mjs`).
- _2026-07-30_ — **`GET /repos/:id/pulls` and `GET /pulls/:id` do a LIVE synchronous GitHub API round-trip on every request** (via octokit, when a token is configured) — even for a repo whose token is expired/invalid or whose GitHub-side name doesn't exist (e.g. a seeded demo repo like `acme/payments-api`), the route still fires the real network call, gets a 404/403, and octokit's retry plugin adds further delay before falling back to persisted rows ("never fail the read" try/catch). Observed this taking 1-2s+ per request in local dev — sometimes much longer under GitHub secondary rate-limiting backoff — versus the near-instant `<10ms` of every other route. Not caused by any specific feature; it's an inherent cost of the always-try-to-sync design. If a page looks stuck on "Loading…" with no client console error, check the API's own request-completed timing in its logs before suspecting the frontend.
- _2026-07-30_ — **Zod `.default()` makes the field required in `z.infer`'s output type, not optional** — it only fills the value at actual `.parse()` time, but any code that builds a plain object literal typed against the inferred TS type (without going through `.parse()`) must supply the field, or TS errors. Bit us on `PrMeta.cost_usd`: since `PrDetail = PrMeta.extend({...})` (`src/vendor/shared/contracts/platform.ts`), switching it from `.nullish()` to `.nullable().default(null)` broke typecheck in `src/adapters/github/octokit.ts`, `src/adapters/mocks.ts`, and the DB-fallback path in `src/modules/pulls/routes.ts` — none of which construct `PrMeta`/`PrDetail` via `.parse()`, they return literals. Fix was to keep `PrMeta.cost_usd` as `.nullish()` (matches the existing `score` field) and reserve `.nullable().default(null)` for schemas that are actually re-parsed at read time (see Recurring Errors & Fixes below). Before adding `.default()` to any shared zod field, check whether the schema (or anything `.extend()`-ing it) is also used as a bare TS type for literals built outside `.parse()`.

## Recurring Errors & Fixes

- _2026-08-21_ — **`findings.start_line`/`end_line` is NOT reliably ordered — roughly 1 in 20 findings in this workspace has `end_line < start_line`** (`SELECT id, title, start_line, end_line FROM findings WHERE end_line < start_line` returned 3 of 53 rows live in this workspace, e.g. `start_line=130, end_line=123` on "Cost usd field semantics silently changed…"). It's a model artefact of the LLM's own output, not a data-entry bug, and nothing upstream normalises it before it lands in `findings`. Any feature that derives a new persisted range FROM a finding's own `start_line`/`end_line` (eval cases, future annotations, etc.) must run it through `min`/`max` normalisation before writing OR searching with it — `eval/helpers.ts::normalizeRange` is the first instance of this, called both before `eval_cases`/`eval_case_expectations` are inserted (the `eval_case_expectations_end_line_check` CHECK requires `end_line >= start_line`) and inside `cutFragment` itself (an inverted range breaks `rangesOverlap`'s hunk search the same way). Don't relax the CHECK constraint to "fix" a future occurrence of this — normalise the input instead, the constraint is what guarantees every stored expectation stays scorable.
- _2026-08-17_ — **`getRunTrace` returned `row.trace as RunTrace` — a cast, not a parse — so every `.default(...)` in the `RunTrace` contract was decorative and legacy `run_traces` documents came back missing keys.** The contract carries two comments (`stats.cost_usd`, 2026-07-30; `specs_excluded`, 2026-08-16) explaining that a field added later must use `.default(...)` "because `.parse()` would otherwise throw on a document persisted before it existed" — but nothing on the read path ever called `.parse()`. The write path does (`platform/trace-builder.ts` ends in `RunTraceSchema.parse(trace)`), which is what made the mitigation look real. Net effect: the client received `specs_excluded: undefined` for every trace written before 2026-08-16 and the drawer threw on `trace.specs_excluded.length`; `cost_usd` had the same latent hole and survived only because `formatCost` tolerates a nullish input.
