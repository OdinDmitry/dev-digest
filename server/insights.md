## What Works

- _2026-08-27_ — **`ReviewRunExecutor.executeRuns` is hermetically testable (no DB, no real Container) by constructing a REAL `Container(loadConfig(...), {} as never, overrides)` plus hand-built `repo`/`agents` objects cast `as unknown as ReviewRepository` / `Container['agentsRepo']`, rather than mocking the whole executor.** Writing `test/run-executor-parallel.test.ts` (T16, `docs/plans/2026-08-27-multi-agent-review.md`), the key unlocks were: (1) every constructor the executor touches transitively (`JobRunner`, `LocalNoAuthProvider`, `PrIntentRepository`, `RepoRepository`, `ContextRepository`) only STORES its `db` argument, never queries it synchronously, so `{} as never` is a safe stand-in for `Db` as long as nothing downstream actually awaits a real query; (2) set `agent.repoIntel = false` on every fixture agent so `runOneAgent` skips `buildCallersDigest`/`buildRepoMapDigest`/`buildRankNote` entirely (their `container.repoIntel` getter would otherwise construct a real `RepoIntelService` needing a real DB); (3) have the fake `repo.getPull` resolve to `undefined` so `IntentService.ensure`'s `requirePull` throws `NotFoundError`, which `executeRuns`'s pre-work try/catch swallows into "no intent" — the batch degrades exactly like a real intent failure, never touching `PrIntentRepository`/`RepoRepository`'s query methods; (4) inject `overrides.git = new MockGitClient({diff: DIFF})` so `loadDiff` succeeds on the FIRST branch (`container.git.diff()` returns non-empty files) and never falls through to `diffFromPrFiles(repo, ...)`, which would otherwise need `repo.getPrFiles` to return something real. With these four in place, only `container.llm` needs a real fixture (a custom `LLMProvider` per test) and only `repo.insertReview`/`insertFindings`/`markReviewed`/`completeAgentRun`/`saveRunTrace` need trivial stubs — no `buildApp()`/Postgres/testcontainers required to exercise the executor's actual `PQueue` fan-out. Reuse this shape for any future hermetic test of `ReviewRunExecutor` or anything else that constructs `IntentService`/`ContextService` inline.
- _2026-08-22_ — **Eval scoring is content-trigger, not zone-overlap** — `scoreCase` passes `must_find` when `groundedCount >= 1` and `must_not_flag` when `groundedCount === 0`; expectation `file`/`start_line`/`end_line` are provenance only (AC-12..14). Precision numerator = all grounded on must_find cases (AC-16). `resolveCaseContext` always returns empty docs; create/from-finding force `repoId: null`; `resolves_context` is always `false` on the DTO (AC-11/46/49/50).
- _2026-08-22_ — **One eval case per seeding finding: service 409 + partial unique index `eval_cases_origin_finding_uq`** — re-clicking "Turn into eval case" used to insert another row with the same `origin_finding_id`. `createFromFinding` now rejects when `findCaseByOriginFindingId` hits; the unique index (WHERE NOT NULL) covers the check-then-insert race (same pattern as `eval_suite_runs_one_active_per_agent`). Seed DTO carries `existing_case_id` so the dialog can disable Save before the POST. Hand-made cases (`origin_finding_id` null) stay unrestricted. Migration `0019_bitter_pete_wisdom.sql` — if apply fails on duplicate rows, delete extras first.
- _2026-08-22_ — **Testing an aggregate-over-workspace endpoint (`EvalService.dashboard`'s `run_all: {agent_count, case_count}`) against `eval-runs.it.test.ts`'s SHARED single-workspace fixture — assert the before/after DELTA, never the absolute count** — the whole `describe` block in that file (and every eval `.it.test.ts` file) shares one `workspaceId` from `seed()` across every `it()`, and `run_all` sums over EVERY agent+case currently in that workspace, including ones earlier tests in the same file already created; the plan's own hard constraint additionally forbids asserting an exact eval-case count anywhere. Snapshotting `GET /evals/dashboard` immediately before creating a test's own fixtures, then asserting `after.run_all.X - before.run_all.X` equals the KNOWN contribution of just the fixtures that test created (e.g. 2 agents / 3 cases, with one zero-case agent contributing nothing), is order-independent and references no global state — it passes identically whether the test runs first or last in the file, and regardless of what sibling tests or seed data already put there. Reuse this delta pattern for any future assertion in this module's `it.test.ts` files that sums or counts over the whole workspace, instead of asserting an absolute number.
- _2026-08-22_ — **The drop-then-create `drizzle-kit generate` workaround (2026-08-04 entry below) also works at TABLE granularity, not just columns** — dropping `eval_runs` and adding `eval_suite_runs`/`eval_case_results` in the SAME schema diff would present the same rename-ambiguity prompt `drizzle-kit` shows for columns (a whole-table version of "created or renamed from X?"). Splitting into two `pnpm db:generate` passes (commit the `DROP TABLE eval_runs` migration alone first, then add the two new tables — plus any non-removing column changes to a THIRD table, `eval_cases`, in the same second pass) produced two clean, non-interactive migrations (`0017_fearless_falcon.sql` DROP-only, `0018_conscious_spitfire.sql` CREATE + ALTER-only) with no hang. Confirms the workaround generalizes past "same table, add+remove columns" to "same migration, drop one table and create others" — split by DROP vs CREATE/ALTER, not by which table is involved.
- _2026-08-17_ — **Project Context listing meets its 2 s / 2 000-file budget with no persisted token cache — measured cold 1,347 ms, warm 466 ms** — measured by mirroring `ContextService.listDocuments`' hot path (`listMarkdown` → `PQueue(READ_CONCURRENCY=16)` of `readDocument` + `TiktokenTokenizer.count` → sort) over a throwaway tree of 2,000 `.md` files across 5 folders, ~1–8 KB each, 722,748 tokens total. "Cold" is a fresh process, where the `${repoId}:${path}:${size}:${mtime}` memo in `service.ts` is empty and every file is read AND BPE-encoded; "warm" is a second pass in the same process, where every file is still re-read but every token count is a memo hit. Cold was the case the plan flagged as at risk and pre-scoped a `context_documents` cache table for — **that follow-up is not needed at this limit on this hardware**, and the ~2.9× cold/warm gap shows BPE encoding, not file I/O, is what the memo removes. Re-measure before raising `DISCOVERY_LIMIT` (2,000) or `MAX_DOCUMENT_BYTES` (256 KB); a corpus of larger documents will move cold much more than warm. An earlier verification pass recorded ~830 ms warm on a different corpus — both are well inside budget, so treat either as an order-of-magnitude fact, not a regression baseline.
- _2026-08-16_ — **Fixed the `readDocument` symlink/junction escape (see Open Questions 2026-08-16) with a second `realpath()`-based containment check, keeping the existing string-prefix check as a cheap fast path** — `modules/context/scan.ts`'s `readDocument` now does `[realRoot, realTarget] = await Promise.all([realpath(rootResolved), realpath(target)])` after the fast-path string check passes, then re-checks `realTarget` starts with `realRoot + sep` before ever calling `stat`/`readFile`. `realpath()` resolves symlinks AND win32 junctions along the whole path, so a junction created inside the working copy pointing outside it now correctly fails the second check and returns `null` (previously it silently followed through). `realpath()` on a nonexistent path throws — caught and treated as `null`, consistent with the function's "never throw" contract. Confirmed against `test/context-scan.test.ts`'s junction repro (previously red, now green) and the full existing suite (188/188 unit tests, no regression).

## What Doesn't Work

## Codebase Patterns

- _2026-08-28_ — **A group-row write in a "create + dispatch" service method must not precede the workspace-scoped existence check, even when the dispatched-to method already performs that check** — `plan-verifier` flagged `startMultiAgentReview` (`modules/reviews/service.ts`, `docs/plans/2026-08-27-multi-agent-review.md` T13) for calling `this.repo.createMultiAgentRun({workspaceId, prId})` BEFORE `this.runReview(...)`, even though `runReview` itself immediately calls `getPull(workspaceId, prId)` and throws `NotFoundError` on a miss. Two concrete failure modes from the ordering alone: an unknown `prId` hits `multi_agent_runs.pr_id`'s FK constraint and falls through to the generic 500 handler instead of the module's usual 404; a `prId` belonging to ANOTHER workspace gets a `multi_agent_runs` row written (associating the requesting workspace with a foreign PR) before the downstream `getPull` rejects — an orphaned but real cross-workspace write, even though it's unreachable afterward via either read path (`multiAgentForPull`/`runReview` both scope correctly). Fixed by adding a duplicate `const pull = await this.repo.getPull(workspaceId, prId); if (!pull) throw new NotFoundError(...)` immediately before `createMultiAgentRun`, accepting the extra query rather than restructuring `runReview`'s signature to accept an already-fetched pull (plan-verifier's fix note explicitly allowed either, preferring the smaller change). Generalize: in any service method that does an early write (a group/parent row, a job enqueue, an audit log) ahead of delegating to a helper that itself validates workspace scope, the validation has to run before the FIRST write in the caller, not just before the helper's own writes — "the helper checks it" is not equivalent to "the caller's write is guarded".

- _2026-08-28_ — **Superseded by re-review, corrects the 2026-08-28 entry below: "forwards into `agentColumnFromRun`" was not enough to call `runsForMultiAgentRun`'s row-typed return settled — `service.ts` was still reading `run.id` off it TWICE (building `reviewsByRunIds`'s argument, and matching a run to its review), which is the same "business logic on a row's own field" category the original finding cited, just on `.id` instead of `.status`/`.finishedAt`.** `agentColumnFromRun(run, ...)` on its own line was genuinely opaque forwarding, but `runRows.map(({run}) => run.id)` (building the query arg) and `reviewByRunId.get(run.id)` (matching inside the map) both READ a field off the row in ring 2, not just forward it. Fixed by adding two more `AgentRunRow`-aware helpers to `helpers.ts`: `runIdsOf(runs): string[]` (the id extraction `reviewsByRunIds` needs BEFORE columns can be built — has to stay a separate step since the review fetch is a prerequisite, not a consumer, of the column-building), and `columnsFromRuns(runRows, reviews): AgentColumn[]` (the whole `reviewByRunId` map-and-match loop, previously inline in `service.ts`, now entirely inside `helpers.ts`). After this, `service.ts`'s `multiAgentForPull` holds `runRows` (still `$inferSelect`-typed) only long enough to pass it opaquely into `runIdsOf`/`columnsFromRuns`/`totalGroupDurationMs` — it never destructures a field off it itself. Generalize past the entry below: "forwards into an accepted mapper" is only a safe reason to leave a row-typed signature alone if EVERY line touching that variable in ring 2 is a bare forward — grep for the row's own field names (`.id`, `.status`, `.ranAt`, ...) against the variable, not just its final destination, before calling a `$inferSelect`-typed return settled.
- _2026-08-28_ — **When a new `reviews`-module read path needs to do arithmetic/comparison logic over Drizzle rows (not just field pass-through), put the LOGIC itself in `helpers.ts` next to the row type, not just the row-to-DTO mapping** — `plan-verifier` flagged `ReviewService.multiAgentForPull` (`docs/plans/2026-08-27-multi-agent-review.md`) for holding `MultiAgentRunRow`/`AgentRunRow` in `service.ts` and running `.every(...)`/`Math.max(...)` directly on raw row fields (`onion-architecture`'s row-type rule, plus this module's "don't add new ring-2 row-type uses" accepted-violations note). `agentColumnFromRun` (`helpers.ts`) was already the precedent for a row→DTO mapper at this boundary, but it only proved the "reshape a row into a DTO" half of the rule — the fix needed a SECOND function, `totalGroupDurationMs(groupRanAt, runs)`, that does the actual comparison/reduction (`allTerminal` check + `Math.max` over `finishedAt`) inside `helpers.ts` and returns a plain `number`, so `service.ts` only ever calls it and never destructures `.status`/`.finishedAt`/`.ranAt` off a run row itself. Separately, `latestMultiAgentRunForPull` (`repository/run.repo.ts`) was changed to map its row to a plain `{id, prId, ranAt}` (`MultiAgentRunGroup`, following the already-established `AgentRunStatsRow`-style plain-interface pattern in the same file) BEFORE returning, rather than exporting `$inferSelect` as `MultiAgentRunRow`. `runsForMultiAgentRun`'s `{run: AgentRunRow, ...}[]` return was deliberately left AS-IS (still forwarded into `agentColumnFromRun`, the accepted boundary) — only the two flagged usages moved. Generalize: when a plan-verifier finding cites specific business-logic lines operating on a row's fields, fix exactly those call sites (move the logic to the module's row-aware helper file), don't reflexively rewrite every row-typed signature the finding's evidence happens to mention in passing.

- _2026-08-27_ — **A "no runtime import" module-purity test (`scoring.ts`'s AC-19 test asserting every `import ` line matches `/^import type /`) survives moving a symbol OUT of the pure module only if the moved symbol's re-export stays a bare `export { x } from './other.js'` — the moment the module needs to CALL that symbol itself, it needs a value-level import, which fails the test.** Moving `Zone`/`normalizeZonePath`/`zonesOverlap` out of `modules/evals/scoring.ts` into `modules/_shared/zones.ts` (T4/T5, `docs/plans/2026-08-27-multi-agent-review.md`) hit exactly this: `scoring.ts`'s own `matchesAny` calls `zonesOverlap` internally, but re-exporting it via `export { zonesOverlap } from '../_shared/zones.js'` creates no local binding to call. Fixed by keeping the public re-export pure (`export { normalizeZonePath, zonesOverlap } from '../_shared/zones.js'`, satisfies external consumers + the purity test) and adding a small **private, unexported** duplicate of the overlap check (`overlapsLocally`) for `matchesAny`'s own internal use — the canonical implementation lives in `_shared/zones.ts` and is what every other module gets; the duplicate is scoped to this one file's self-imposed purity constraint. Before assuming "move + re-export" is enough when a plan says "re-export so the test keeps passing unchanged", check whether the OWNING module also calls the symbol itself, not just forwards it.

- _2026-08-28_ — **`drizzle-kit generate` stayed non-interactive for `ci_runs`' Phase B diff even though it both ADDS 15 columns and SETS NOT NULL on 2 existing (already-empty) ones (`status`, `github_url`) — only REMOVE/RENAME triggers the 2026-08-04 hang, not `ALTER COLUMN ... SET NOT NULL`** — confirms and extends the 2026-08-28 `ci_installations` entry below: a `SET NOT NULL`/`SET DEFAULT` on a column that already exists (no rename ambiguity, nothing to match against) generates a plain `ALTER TABLE ... ALTER COLUMN` statement, indistinguishable from an ADD in terms of triggering the interactive prompt. Migration `0022_steep_molten_man.sql` — 1 pass, no split needed.
- _2026-08-28_ — **`CiRun`'s `repo` field is NOT a column on `ci_runs` — it has to come from a LEFT JOIN against `ci_installations`** — the Frozen contract for Phase B's `CiRun` (`docs/plans/2026-08-28-export-to-ci-b-runner-and-ingest.md`) added `repo: z.string()` to the DTO, but the `ci_runs` table itself (T3) has no `repo` column (only `ci_installation_id`, which cascades `set null` on installation delete). `CiRepository`'s read methods (`listRunsForWorkspace`/`listRunsForAgent`) now do a second `leftJoin(t.ciInstallations, eq(t.ciInstallations.id, t.ciRuns.ciInstallationId))` alongside the existing `agents` join (for `agent_name`), and `ciRunToDto` takes `repo: string | null` as a third parameter, falling back to `''`. Both joins are LEFT (not INNER) because `agent_id`/`ci_installation_id` are both nullable via `onDelete: 'set null'` — an inner join would silently drop a CI run's whole row from the list the moment its agent or installation is deleted. - _2026-08-28_ — **`agent-runner` cannot import `server/src/modules/ci/ingest.ts`'s `verdictFromEvent` (payload.event → CiVerdict) even though the logic is identical on both sides — duplicate the ~8-line pure function instead of reaching across the package boundary** — `agent-runner/CLAUDE.md`'s "Consuming reviewer-core" section is explicit that the only two things this package resolves outside `node_modules/@devdigest/*` are `@devdigest/reviewer-core` and `@devdigest/shared`, both aliased to raw source specifically so `ncc build` can inline them into a self-contained `dist/index.js` with zero runtime `@devdigest/*` imports; `server/src/modules/ci/` is server application code, never bundled, and importing from it would either break the `ncc` build or silently pull in a `db/schema`-adjacent dependency chain. `run.ts` now has its own private `verdictFromEvent`, with a doc comment pointing at the server's copy and explaining why it's duplicated rather than shared. - _2026-08-28_ — **Superseded by architecture-reviewer fix: `CiServiceDeps.db` was removed, `repos: RepoRepository` added instead** — the 2026-08-28 entry directly below flagged the plan-frozen `db: Db` + raw `t.repos` query in `CiService.requireRepo` as a deliberate-but-flagged onion-architecture bend. `architecture-reviewer` graded it CRITICAL (not covered by the accepted-violations list, which is scoped to existing `reviews`/`repos` row-type-in-signature cases and explicitly says "do not add new ones" — a service constructing and running its own query is a heavier violation than a row type threaded through a signature). Fixed by following the exact pattern `evals/service.ts` already uses: added `repos: RepoRepository` to `CiServiceDeps`, constructed `new RepoRepository(app.container.db)` in `ci/routes.ts` (mirroring `evals/routes.ts`), and `requireRepo` now calls `this.deps.repos.getById(workspaceId, repoId)`. `db: Db` was dropped from `CiServiceDeps` entirely — `requireRepo` was its only caller in `service.ts`. `RepoRow` is now imported from `repos/repository.ts` (already exported there) instead of re-derived via `typeof t.repos.$inferSelect`. - _2026-08-28_ — **A frozen-surface `service.ts` deps type can explicitly include `db: Db` alongside a narrow repository, and that's a deliberate bend of `onion-architecture`'s "ring 2 has no technology imports" rule — not something to "fix" by inventing a repository the plan didn't ask for** — `docs/plans/2026-08-28-export-to-ci-a-contracts-generation-install.md` T14 froze `CiServiceDeps` as `{ repo: CiRepository; agents: AgentsRepository; skills: SkillsRepository; db: Db; github: () => Promise<GitHubClient>; config: Pick<AppConfig,'runnerBundlePath'> }` with NO `RepoRepository`, even though the install sequence's step 2 ("`repos` row by `(workspaceId, repo_id)`") genuinely needs one. `CiRepository` (the `repo:` key) only owns `ci_installations` (T13's scope). - _2026-08-28_ — **`drizzle-kit generate` did NOT hang or prompt interactively for `ci_installations`' add-only diff (workspace_id NOT NULL FK + 4 more columns + 2 indexes)** — unlike the 2026-08-04 entry below (same-table diffs that BOTH add and remove columns trigger the un-completable rename prompt on this sandboxed Bash tool), a pure ADD-only diff across 5 new columns + a unique index + a plain index generated cleanly and non-interactively in one pass (migration `0021_fresh_enchantress.sql`). - _2026-08-22_ — **A multi-step cross-package verification script (`scripts/verify-l06.mjs`, `pnpm verify:l06`) needs `spawnSync(cmd, args, { cwd, shell: true })` per step, not a single shelled-out command string** — `pnpm`/`vitest` resolve to `.cmd`/`.ps1` shims on win32, so `spawnSync("pnpm", [...])` without `shell: true` fails to launch at all on Windows even though it works on POSIX; adding `shell: true` fixes that without needing `&&`/`cd` to chain steps or change directories — each step instead gets its own explicit `cwd` option (`server/` vs `client/`), which is what the plan's constraint 16 ("behaves identically under PowerShell, cmd and bash") is actually asking for. `shell: true` on a SINGLE command (no chaining operators inside the command string itself) satisfies that constraint; it's the `&&`/`cd` chaining across steps that differs between shells, not the presence of `shell: true` on one invocation.
- _2026-08-22_ — **`AssembledRunContext.excluded`'s `ContextExclusionReason` is a closed 3-value enum (`absent`/`other_repo`/`over_budget`) — it cannot express "the resolver itself threw"** (e.g. `ContextService.assembleForRun` throwing `NotFoundError` when a case's `repo_id` points at a deleted repo, `docs/plans/2026-08-22-eval-pipeline-b-suite-runs.md` constraint 4). Implementing the eval suite runner's per-case context resolution (`modules/evals/runner.ts`'s `resolveCaseContext`), tried returning `AssembledRunContext` directly from a try/catch wrapper and hit a TS error constructing the exclusion — `reason: 'context unavailable: ...'` isn't a member of the enum. Fixed by defining a broader local `ResolvedCaseContext` shape (`excluded: EvalContextExclusion[]`, whose `reason` is `z.string()`, not the narrow enum) instead of reusing `AssembledRunContext` end-to-end. Any future caller that wraps `assembleForRun` in its own try/catch and wants to report the throw as a normal exclusion (rather than letting it propagate) needs the same broader type — don't force the narrow `ContextExclusionReason` enum to carry a free-text failure reason.
- _2026-08-22_ — **A new ring-2 service narrowed to `Pick<Container, 'git'|'config'>` (per `onion-architecture`'s "Dependencies of a service") cannot be passed directly into `modules/reviews/diff-loader.ts`'s `loadDiff(container: Container, ...)` — its parameter type is the FULL `Container`, and `diff-loader.ts` is a read-only reference pattern (do-not-modify per `docs/plans/2026-08-22-eval-pipeline-a-foundation.md`'s Out-of-scope)** — `Pick<Container,'git'|'config'>` is NOT structurally assignable to `Container` (it's missing every other member: `db`, `secrets`, `auth`, `agentsRepo`, `llm()`, etc.), so calling `loadDiff(this.deps.container, ...)` from `modules/evals/service.ts` fails to typecheck even though `loadDiff` only ever reads `.git` off it. Resolved with a narrow cast at the two call sites (`this.deps.container as unknown as Container`) rather than widening the service's own dependency type or touching `diff-loader.ts` — the service's public dependency contract stays honest (`Pick<Container,'git'|'config'>`, matching what `onion-architecture` calls "the acceptable shorthand"), and the cast is safe because the underlying object really does carry a working `.git` (the composition root passes the real `Container` in `routes.ts`; only tests/mocks need to supply an object satisfying the Pick). Any future service that needs to call an existing full-`Container`-typed helper (not just `loadDiff`) while itself declaring a narrowed dependency type will hit the same mismatch — cast at the call site, don't widen the dependency type.
- _2026-08-17_ — **`ContextService.assembleForRun` (the run-time resolver, `docs/plans/2026-08-16-project-context-run-injection.md` U5) deliberately does NOT write into the private `tokenCache` Map that `listDocuments`/`countTokens` use** — that cache is keyed `${repoId}:${path}:${sizeBytes}:${mtimeMs}`, and the size/mtime come from the directory-walk `stat` that `listMarkdown` already did; `assembleForRun` only has `readDocument`'s return (text, no stat metadata), and adding a second fs.stat call per document to build a compatible key would mean touching `scan.ts` (out of this task's file scope: only `helpers.ts`/`service.ts`). ## Tool & Library Notes

- _2026-08-28_ — **`octokit.rest.actions.downloadArtifact()`'s generated TS response type is USELESS for the actual bytes — its OpenAPI-derived `responses` shape is `302: { content: never }`, because the spec only documents the redirect, not what's at the far end of it** — Octokit's underlying fetch transport follows the redirect transparently (default `redirect` behavior), so `download.data` at runtime genuinely is the artifact zip's `ArrayBuffer`, but the type system has no way to express that from the generated types. `octokit.ts`'s `downloadRunArtifactEntry` casts with `new Uint8Array(download.data as unknown as ArrayBuffer)` — a deliberate, documented `as unknown as` because the OpenAPI spec and the actual runtime behavior diverge here, not sloppy typing. - _2026-08-28_ — **A `drizzle-orm` `and(...)` call always types as `SQL<unknown> | undefined` (never bare `SQL`) even when called with ≥2 conditions, because the same overload also has to support a variadic call with zero arguments** — writing a private helper that accepts a pre-built `where` clause (`CiRepository.runsWithAgentAndRepo`) and typing its parameter as `SQL` (not `SQL | undefined`) fails `tsc` at every call site, even ones that always pass a real condition — the compiler checks the PRODUCER's declared return type, not what a specific call site happens to produce. - _2026-08-27_ — **Drizzle 0.38's `PgSelectQueryBuilderBase` has no `.distinctOn()` chain method — the DISTINCT ON columns are an argument to `db.selectDistinctOn(cols, fields)` on the `db` object itself, not a builder method after `.select()`.** Needed for `lastSuccessfulRunByAgent` (`modules/reviews/repository/run.repo.ts`, T8) — "each agent's last successful run" is `DISTINCT ON (agent_id) … ORDER BY agent_id, ran_at DESC, id DESC`. - _2026-08-05_ — **Node's built-in `net.BlockList` (Node 15+) is the right primitive for an SSRF address allowlist/denylist — don't hand-roll CIDR math** — `adapters/webfetch/https.ts`'s `isBlockedAddress()` builds one `BlockList` with `addSubnet`/`addAddress` calls for the private/loopback/link-local/CGNAT/multicast ranges, IPv4 and IPv6 both, and `blockList.check(ip, family)` handles IPv4-mapped IPv6 literals (`::ffff:10.0.0.5`) correctly against the IPv4 rules without any extra unwrapping code. `node:net`'s `isIPv4`/`isIPv6` are enough to pick the family to pass to `check()`. - _2026-08-04_ — **fflate's `unzipSync({ filter })` runs against the central directory BEFORE decompression, which is exactly where an "untrusted archive" policy belongs** — the filter callback receives `{ name, size, originalSize, compression }` and returning `false` means those bytes are never inflated at all, so `modules/skills/import.ts` can promise that executable archive members are not merely ignored but never read. - _2026-07-30_ — **Zod `.default()` makes the field required in `z.infer`'s output type, not optional** — it only fills the value at actual `.parse()` time, but any code that builds a plain object literal typed against the inferred TS type (without going through `.parse()`) must supply the field, or TS errors.
