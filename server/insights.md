## Codebase Patterns

- _2026-08-05_ — **A "compute-if-absent" method needs its OWN workspace check on the cache-hit branch — copying a sibling method's shape doesn't copy its guard** — `IntentService.ensure()` (`modules/intent/service.ts`) originally read `this.deps.intents.getByPrId(prId)` (keyed on `pr_id` alone) and returned the cached row directly on a hit, with no `requirePull(workspaceId, prId)` call on that branch, even though the neighboring `get()` and `computeAndPersist()` both call `requirePull` first. Result: `POST /pulls/:id/intent` for a PR id belonging to ANOTHER workspace would silently return that workspace's intent instead of throwing `NotFoundError`, once any intent for that PR had been computed once — a cross-workspace data leak. Caught by architecture/plan-verifier review, not by a test (the `.it.test.ts` that would have exercised this was skipped this iteration for scope reasons — see Open Questions). Fixed by adding `await this.requirePull(workspaceId, prId)` as the first line of `ensure()`. Before adding any new method to a workspace-scoped repository/service that reads-then-maybe-computes, check that EVERY early-return branch independently enforces the workspace scope — don't assume it's inherited from a sibling method's overall shape.
- _2026-08-05_ — **`reviews/repository.ts` (via `reviews/repository/pull.repo.ts`) already had an `upsertIntent`/`getIntent` pair against `pr_intent` before the intent-layer feature was implemented** — same "pre-built, unit-tested-or-not, unused" scaffolding pattern already logged above for `pulls/status.ts`'s `rollupSeverities`. Nothing in the codebase called it. The L03 intent-layer plan specified a brand-new `modules/intent/repository.ts` (`PrIntentRepository`) owning the same table, and that is what got built — the older `reviews` accessors were left untouched (in scope only for `run-executor.ts`) rather than deleted, so `pr_intent` now has two independent read/write paths in the repo. Before adding a repository method against a table that already has a sibling module, grep the WHOLE codebase for the table name first (`grep -rn prIntent src`, or the Drizzle table identifier generally) — a hit outside the module you're building usually means either reuse it or explicitly decide (and say so) that you're leaving it as dead scaffolding, rather than discovering the duplication after the fact.
- _2026-08-04_ — **A "list stats" endpoint and a "list" endpoint must be registered in that order, or the stats route silently 404s/422s through the `:id` route** — `GET /skills/stats` has to be declared before `GET /skills/:id` in `modules/skills/routes.ts` (same rule already applied to `GET /agents/stats` vs `/agents/:id`). find-my-way generally prefers a static segment over a param, so this hasn't actually bitten in practice on either module — but it's a hazard worth a comment at BOTH call sites (search for "so the static segment can never be read as a uuid") rather than trusting the router's tie-break silently forever, since a route ordering refactor could invert it.
- _2026-08-04_ — **`AgentStats` was already taken in `contracts/observability.ts` before the skills lesson needed the name** — adding an `AgentStats` to `contracts/knowledge.ts` for the agent-card rollup (skill/run/cost) compiled fine on its own but broke the barrel with `TS2308: Module './contracts/knowledge.js' has already exported a member named 'AgentStats'`, because `src/vendor/shared/index.ts` re-exports every contract file with `export *`. The existing one is the far richer L07 per-agent detail payload (accept rate, severity breakdown, trend) for `GET /agents/:id/stats`. Resolved by naming the new one `AgentListStats` and its route `GET /agents/stats`, leaving the L07 contract and route untouched. Before adding any contract type, grep the whole `contracts/` folder for the name — a collision surfaces only at the barrel, not in the file you edited, and several scaffolded-but-unused contracts already occupy obvious names.
- _2026-08-04_ — **`skill_versions` can only meaningfully version the body, unlike `agent_versions`** — the agents module bumps its version on ANY config field change (`isConfigChange`, `agents/helpers.ts`) because `agent_versions.config_json` snapshots the whole config. `skill_versions` has only `(skill_id, version, body)`, so versioning a rename would write two byte-identical snapshots. `skills/helpers.ts::isBodyChange` is deliberately narrower — rename/retype/enable-disable return the same version. Don't "fix" the asymmetry by copying `isConfigChange` over.
- _2026-07-30_ — **"Latest review by `createdAt`" is misleading once a PR has more than one agent** — `GET /repos/:id/pulls`'s `score`/`cost_usd`/`findings_by_severity` all originally picked whichever `reviews` row was newest overall. On a real multi-agent PR (3 agents run together), the agent that happened to finish LAST had 0 findings/score 100, while an agent that finished a minute earlier had rejected the PR with real findings — the list showed a clean "Reviewed/100/—" for a PR that was actually rejected. Fixed `cost_usd`/`findings_by_severity` to sum across each agent's OWN latest review (group by `agent_id`, first-seen-per-group in newest-first order, fall back to the review's own id when `agent_id` is null so it never merges with another). `score` deliberately stays "latest overall" — there's no obvious single-number way to combine multiple agents' scores. Verified live against real seeded data (`docker exec devdigest-postgres psql ...`) before concluding it was a real gap, not a bug in the new code.
- _2026-07-30_ — **`src/modules/pulls/status.ts` already had `rollupSeverities`/`SeverityCounts` — pre-built, unit-tested, and unused** — while wiring `findings_by_severity` into `GET /repos/:id/pulls` for the severity-counters feature, found this exact pure tally function (CRITICAL/WARNING/SUGGESTION counts, ignoring unknown severities) already sitting in `status.ts` with its own passing tests in `pulls-status.test.ts`, despite the route itself carrying a comment that severity breakdown was "intentionally not surfaced." It predates any caller — a course-scaffold stub for a not-yet-built lesson exercise. Before writing new severity/rollup logic anywhere in the `pulls` module, check `status.ts` first; it's very likely already there and tested.

## Tool & Library Notes

- _2026-08-05_ — **Node's built-in `net.BlockList` (Node 15+) is the right primitive for an SSRF address allowlist/denylist — don't hand-roll CIDR math** — `adapters/webfetch/https.ts`'s `isBlockedAddress()` builds one `BlockList` with `addSubnet`/`addAddress` calls for the private/loopback/link-local/CGNAT/multicast ranges, IPv4 and IPv6 both, and `blockList.check(ip, family)` handles IPv4-mapped IPv6 literals (`::ffff:10.0.0.5`) correctly against the IPv4 rules without any extra unwrapping code. `node:net`'s `isIPv4`/`isIPv6` are enough to pick the family to pass to `check()`. No new dependency needed.
- _2026-08-04_ — **`drizzle-kit generate` hangs forever on stdin from this sandboxed Bash tool whenever a schema diff both removes and adds columns on the same table** — it prompts an interactive arrow-key "created or renamed from X?" question per new column when a same-table diff has any removed columns to match against, and neither `printf '\n'` nor `yes ""` piped into it resolves the prompt here (the TUI reads raw keypresses, not lines, so a non-TTY stdin just hangs rather than being consumed). Confirmed by killing the process and retrying. Workaround: split the schema edit into two separate `db:generate` passes — first commit ONLY the column removal (produces a clean `DROP COLUMN` migration, no prompt, since nothing new exists yet to rename FROM), then edit again to add the new columns (clean `ADD COLUMN` migration, no prompt, since nothing was removed in that diff). Used successfully for the `conventions` table's `accepted:boolean` → `status:enum` + evidence-line-numbers change (migrations `0013`/`0014`).
- _2026-08-04_ — **fflate's `unzipSync({ filter })` runs against the central directory BEFORE decompression, which is exactly where an "untrusted archive" policy belongs** — the filter callback receives `{ name, size, originalSize, compression }` and returning `false` means those bytes are never inflated at all, so `modules/skills/import.ts` can promise that executable archive members are not merely ignored but never read. Two caveats: `originalSize` comes from the zip header and is attacker-controlled, so the decompressed length must be re-checked afterwards (and a running total kept across members); and fflate's `zipSync({ mtime })` rejects the epoch with `Error: date not in range 1980-2099` — the zip timestamp format starts at 1980, so a "fixed timestamp for reproducible archives" must be an in-range date, not `0` (bit `scripts/build-skill-fixture.mjs`).
- _2026-07-30_ — **`GET /repos/:id/pulls` and `GET /pulls/:id` do a LIVE synchronous GitHub API round-trip on every request** (via octokit, when a token is configured) — even for a repo whose token is expired/invalid or whose GitHub-side name doesn't exist (e.g. a seeded demo repo like `acme/payments-api`), the route still fires the real network call, gets a 404/403, and octokit's retry plugin adds further delay before falling back to persisted rows ("never fail the read" try/catch). Observed this taking 1-2s+ per request in local dev — sometimes much longer under GitHub secondary rate-limiting backoff — versus the near-instant `<10ms` of every other route. Not caused by any specific feature; it's an inherent cost of the always-try-to-sync design. If a page looks stuck on "Loading…" with no client console error, check the API's own request-completed timing in its logs before suspecting the frontend.
- _2026-07-30_ — **Zod `.default()` makes the field required in `z.infer`'s output type, not optional** — it only fills the value at actual `.parse()` time, but any code that builds a plain object literal typed against the inferred TS type (without going through `.parse()`) must supply the field, or TS errors. Bit us on `PrMeta.cost_usd`: since `PrDetail = PrMeta.extend({...})` (`src/vendor/shared/contracts/platform.ts`), switching it from `.nullish()` to `.nullable().default(null)` broke typecheck in `src/adapters/github/octokit.ts`, `src/adapters/mocks.ts`, and the DB-fallback path in `src/modules/pulls/routes.ts` — none of which construct `PrMeta`/`PrDetail` via `.parse()`, they return literals. Fix was to keep `PrMeta.cost_usd` as `.nullish()` (matches the existing `score` field) and reserve `.nullable().default(null)` for schemas that are actually re-parsed at read time (see Recurring Errors & Fixes below). Before adding `.default()` to any shared zod field, check whether the schema (or anything `.extend()`-ing it) is also used as a bare TS type for literals built outside `.parse()`.

## Recurring Errors & Fixes

- _2026-08-04_ — **`ORDER BY colA DESC, colB DESC` with no further tiebreaker returns a DIFFERENT row order across otherwise-identical queries whenever rows tie on both columns** — Postgres makes no ordering guarantee beyond what's specified, and a single LLM extraction batch commonly produces several rows with identical `confidence` and the same `createdAt` (batch-inserted together). `ConventionsRepository.listByRepo` (`modules/conventions/repository.ts`) ordered by `confidence DESC, createdAt DESC` alone, so accepting/rejecting one candidate (which triggers a refetch, not a client-side resort) made unrelated rows visibly swap position on screen — read as a client bug but was purely the DB's unstable tie order. Fix: always append the primary key (`id`) as a final `.orderBy()` column when the sort key isn't already unique — check any other list endpoint sorting by a non-unique column (e.g. `rank`, `score`) for the same gap.
- _2026-07-30_ — **`RunStats.cost_usd` needed `.nullable().default(null)`, not plain `.nullable()`** — `run_traces.trace` (`src/db/schema/runs.ts`) is a JSONB document persisted ONCE at run completion, so rows written before `cost_usd` existed literally lack the key (absent, not `null`). `RunTrace.parse()` on a legacy trace throws with `.nullable()` alone; `.nullable().default(null)` resolves a missing key to `null` instead. Applies to any field added later to `RunStats`/`RunSummary` (`src/vendor/shared/contracts/trace.ts`) that gets read back from a previously-persisted trace — use `.default()` there, not on `PrMeta`-like schemas that are recomputed fresh per request (see Tool & Library Notes above for why those differ).
- _2026-07-30_ — **After a schema revert, the live DB can still have the column** — `pnpm db:migrate` isn't undone by reverting `src/db/schema/*.ts` (e.g. via a branch switch or manual file transfer). Confirmed directly: `agent_runs.cost_usd` still existed in the running Postgres container (`docker exec devdigest-postgres psql -U devdigest -d devdigest -c '\d agent_runs'`, credentials from `docker exec devdigest-postgres env | grep POSTGRES`) even after `schema/runs.ts` on disk had no `costUsd` field. Drizzle doesn't complain about an unknown extra DB column, and `drizzle-kit generate` won't propose dropping it unless the migration snapshot metadata (`db/migrations/meta/`) also reflects the revert — check `\d <table>` directly if something seems off after a branch switch/rebase, don't trust `schema.ts` alone.
- _2026-07-30_ — **`db/migrate.ts`/`db/seed.ts` CLI-entrypoint check regresses easily to a Windows-broken form** — the correct check is `if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href)` (commit `1361d98 fix(dev): fix Windows-broken db scripts`). If it ever reads `if (import.meta.url === \`file://${process.argv[1]}\`)` instead, `pnpm db:migrate`/`pnpm db:seed` silently no-op when run directly on Windows (backslashes + drive letter don't match a `file://` template literal). Seen reappear after a manual cross-branch file transfer that had nothing to do with these files — worth diffing both against HEAD specifically after any manual (non-git-native) file transfer on this repo.

## Open Questions

- _2026-08-05_ — **Running the full `.it.test.ts` suite in parallel (11 Testcontainers Postgres containers) makes `reviews.it.test.ts` and `severity-counts.it.test.ts` intermittently fail on Windows, unrelated to the change under test** — both pass reliably standalone (`pnpm exec vitest run test/reviews.it.test.ts`) and pass on an unmodified checkout run standalone; running the WHOLE suite together on this machine reproducibly drops a different one or two assertions per run (`waitForPrRuns`-style polling not settling, or a background review's findings not yet persisted when the test reads them back). Before concluding a new change broke an unrelated `.it.test.ts` file, re-run that ONE file alone first — the full-suite run is not currently a reliable regression signal on this box.
