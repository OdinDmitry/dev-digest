## What Works

- _2026-08-08_ — **A CI-faithful repro of `.github/workflows/e2e-web.yml` runs locally in one `node:22` container, which is the only way found to reproduce Linux-CI-only flow failures** (`08-skills` failed in CI while passing on Windows against both `next dev` and a real prod build). Recipe: `docker network create ddci`; ephemeral `pgvector/pgvector:pg16` as `ddci-pg` on it; `docker run -d --network ddci -w //work node:22 sleep infinity` (Git Bash needs `MSYS_NO_PATHCONV=1` and the `//work` double slash, or Docker rejects the workdir as `C:/Program Files/Git/work`); ship the tree in with `git archive HEAD -o repo.tar` + `docker cp` (never a bind mount — an in-container `pnpm install` would overwrite the host's Windows-built `node_modules`); `corepack prepare pnpm@10 --activate`; then the workflow's own steps with `DATABASE_URL=postgres://devdigest:devdigest@ddci-pg:5432/devdigest`. Two things the workflow gets for free that the container doesn't: `agent-browser install --with-deps` does **not** pull Chrome's shared libraries there, so add `apt-get install -y libnspr4 libnss3 libdbus-1-3 libatk1.0-0 libatk-bridge2.0-0 libcups2 libdrm2 libxkbcommon0 libxcomposite1 libxdamage1 libxfixes3 libxrandr2 libgbm1 libpango-1.0-0 libcairo2 libasound2 libatspi2.0-0 fonts-liberation` (symptom otherwise: `chrome: error while loading shared libraries: libnspr4.so`, surfacing as every flow failing on its first `open`); and start the API/web with `docker exec -d`, since a backgrounded `&` inside `docker exec`/the Bash tool dies with its shell. Reproduced CI's 8/9 exactly, first run. Also note `scripts/e2e.sh` runs the web with `next dev` while CI runs a production `next build && next start` — build-mode-sensitive bugs will pass locally and fail in CI.
- _2026-08-07_ — **`run.ts` now resolves the native `agent-browser` executable itself, so the Windows `AGENT_BROWSER_BIN` workaround below (2026-08-05) is no longer needed** — `resolveBin()` returns `AGENT_BROWSER_BIN` when set, the plain name on POSIX (unchanged), and on win32 walks `PATH` for a real `agent-browser.exe` first, then falls back to reading npm's generated `agent-browser.cmd` shim and extracting the `.exe` path out of its `"%~dp0…" %*` line. `execFile` then spawns that binary directly. Deliberately NOT `shell: true`: that also fixes the spawn, but concatenates argv unescaped (Node `DEP0190`), and flow steps pass arbitrary text (`find text …`, assertion strings) that contains spaces and quotes — so it would have traded a hard failure for silent mis-parsing of specific steps. When nothing resolves, it returns the plain name so the failure stays the familiar "is agent-browser installed?" `ENOENT`. Verified with a full `./scripts/e2e.sh`: 9/9 flows green on Windows, first time the suite has run here.

## What Doesn't Work

- _2026-08-08_ — **`find role <role> click --name <substring>` does NOT scroll its target into view either — the 2026-08-08 entry under "Recurring Errors & Fixes" below is wrong on that point, and `08-skills.flow.json` step 9 only *appeared* fixed by it** — no agent-browser click command (`click @eN`, `click <css>`, `find … click`) scrolls first: it resolves the element, dispatches a mouse click at its center coordinates, and reports `✓ Done` **without verifying it hit the element**. With the `test-coverage-rubric` card clipped out of the rail's scroll region its rect was `y=1049` against a 577px-tall viewport, so the click landed on `<html>` (verified with a capture-phase document listener: `HTML. phase-doc`, and the row's own listener never fired) — zero selection, zero scroll, exit 0, and the failure surfaced one step later as `wait --url id=` timing out. `agent-browser scrollintoview <sel>` exists but takes a CSS selector or `@eN` ref, neither of which a static flow JSON can express for these inline-styled rows. **Fix used: filter the list with its own search box first** (`find placeholder "Search skills…" fill "test-coverage-rubric"`), which leaves the single matching card at the top of the rail, in view — viewport- and list-length-independent, and it covers the rail's filter on the way. Note `find placeholder`/`find label` match **exactly**, unlike `find role --name` (case-insensitive substring): `"Search skills"` finds nothing, the full `"Search skills…"` (U+2026, not three dots) is required, and that character survives `execFile` argv on both Linux and Windows. This is also why a stale `find text` vs `find role` conclusion was reached earlier: both were no-ops, `find text` just failed loudly (element-not-found) while `find role` failed silently.

## Tool & Library Notes

- _2026-08-05_ — **A globally `npm i -g agent-browser`-installed CLI cannot be spawned by name on Windows via `run.ts`'s `execFile` — neither the extensionless shim nor the `.cmd` shim works, only the native `.exe` does** — `npm`'s Windows global-bin install produces THREE files (`agent-browser` bare — a POSIX shell script, useless to `CreateProcess`, → `spawn ... ENOENT`; `agent-browser.cmd` — a batch shim `%~dp0node_modules\agent-browser\bin\agent-browser-win32-x64.exe %*`, which Node's `execFile`/`spawn` refuses to run without `shell: true` since the Node CVE-2024-27980 fix, → `spawn EINVAL`; `agent-browser.ps1`, not directly executable either). The actual native binary is one directory deeper: `<npm prefix>/node_modules/agent-browser/bin/agent-browser-win32-x64.exe` — point `run.ts`'s `AGENT_BROWSER_BIN` env var directly at that `.exe` (e.g. `AGENT_BROWSER_BIN="$(npm config get prefix)/node_modules/agent-browser/bin/agent-browser-win32-x64.exe" ./scripts/e2e.sh`) and it runs with no further changes. `npm config get prefix` gives the install root (`node_modules/agent-browser/bin/` under it).

## Recurring Errors & Fixes

- _2026-08-08_ — **`find text <name> click` does NOT scroll an off-screen target into view before clicking — `find role <role> click --name <name>` does** — `08-skills.flow.json` clicked the seeded `test-coverage-rubric` skill card via `find text "test-coverage-rubric" click`. That skill is alphabetically last of the 7 seeded skills (`GET /skills` is `ORDER BY name`), so its card sits below the fold in the Skills rail's own scrollable region (`clientHeight` ~415px vs `scrollHeight` ~1055px at agent-browser's default 1264×569 viewport) — confirmed the rail's height is CSS-fixed, not viewport-proportional (still failed 4/4 at a 1280×900 viewport). This reproduced 100% reliably (0/10+ passes) against a **production** build (`next build && next start`, matching `.github/workflows/e2e-web.yml`) but not against `next dev` locally, which is why it passed in this repo's earlier dev-mode runs and only started failing once CI actually ran it — the underlying click behavior doesn't depend on build mode, dev-mode runs just hadn't hit it. Diagnosed by extracting the element's `@eN` ref from `snapshot` and calling `scrollintoview @eN` then `click @eN` by hand — that combination passed 4/4, proving the element itself was fine and only the locate-and-click path was the problem. **Fix: use `find role <role> click --name <substring>` instead of `find text <substring> click` for anything that might not already be scrolled into view** — `find role` resolves through the same accessibility-tree/actionability path Playwright's own role locators use, which auto-scrolls before clicking; `find text` does not. `08-skills.flow.json` already used `find role button click --name "Preview"` for its OTHER click (step 11) — step 9 was the one inconsistent holdout. Prefer `find role` over `find text` by default for any click target in a scrollable list; reserve `find text` for elements already guaranteed to be near the top of the viewport. Two follow-up debugging traps hit while isolating this, worth naming so they aren't re-chased: (1) `pnpm build` run twice against the same `.next/` output directory without a full `next start` process restart in between leaves a stale server process referencing old chunk hashes that no longer exist on disk — manifests as a browser-side `ChunkLoadError`/"Application error" that looks like a real app crash but is purely a stopped/restarted-process artifact; (2) starting the API for a manual repro without exporting `WEB_PORT` leaves its CORS `Access-Control-Allow-Origin` on the default origin, silently blocking every fetch from a web server on a different port with no status code recorded against the request — always export `WEB_PORT` (not just `API_PORT`) when standing up an ad hoc isolated stack, exactly as `scripts/e2e.sh` already does.
- _2026-08-05_ — **A `find text ... click` on the PR-list row with no preceding `wait --text` for that same text is an intermittent race, not a reliable click** — `GET /repos/:id/pulls` does a live synchronous GitHub round-trip per request (documented in `server/insights.md`, sometimes 1-2s+), so the row's title may not be in the DOM yet the instant `find` runs, even though the URL has already changed to `/pulls`. `02-repo-pulls-detail.flow.json` already had a `wait --text "Add rate limiting to public API endpoints"` step before its click and never failed; `04-pr-findings.flow.json` and `05-pr-diff.flow.json` were missing it and failed intermittently (confirmed: fixing one exposed the same latent race in the other on the very next run, then both stabilized once fixed) — 3 consecutive full runs green after adding the wait to all three PR-list-opening flows. Any NEW flow that opens a PR from `/pulls` must `wait --text <PR title>` immediately before the `find ... click`, never click right after `wait --url /pulls`.
- _2026-08-05_ — **Opening a Skill card lands on its Config tab (name/description/type), not Preview — the skill's `body` markdown only renders after an explicit tab switch** — `08-skills.flow.json` expected `body` text ("Enumerate a branch for each of", from `TEST_COVERAGE_RUBRIC.body` in `server/src/db/seed-skills.ts`) to appear right after clicking the skill card, but that text lives in the `PreviewTab`, and `SkillDetail.tsx` defaults to the `config` tab. Fixed by adding `["find", "role", "button", "click", "--name", "Preview"]` before the `wait --text` assertion, same "Tabs kit renders plain buttons, not role=tab" pattern already used for the Agents-editor Skills tab in `09-agent-skills.flow.json`. Any flow asserting on a skill's `body` (as opposed to its `description`, which IS visible on Config) needs this same tab switch.
