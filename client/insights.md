## What Doesn't Work

- _2026-07-30_ — **Portaling a hover-popup to `<body>` (to escape an ancestor's `overflow: hidden`) breaks the usual "parent `onMouseEnter`/`onMouseLeave`" hover pattern** — once the popup is `createPortal`'d out to `document.body`, it's no longer a DOM descendant of the trigger, so an instant `setHovering(false)` on the trigger's `onMouseLeave` unmounts the popup before the mouse has actually reached it (the browser's leave-before-enter event ordering means the popup can vanish mid-transition, with no element left to catch its `mouseenter`). Adding matching `onMouseEnter`/`onMouseLeave` to the popup itself is necessary but NOT sufficient. Fix: debounce the close (`setTimeout(~120ms)` in the leave handler) and cancel it from either element's `onMouseEnter` — see `SeverityCounts.tsx`. Any future portaled hover-UI in this app needs the same debounce, not just mirrored handlers.
- _2026-07-30_ — **When a server aggregation's SEMANTICS change, grep the client for every independent re-derivation of the same metric** — changed the PR-list route's findings/cost aggregation from "latest review overall" to "latest review per agent, summed" (see server `insights.md`), but two client-side spots independently re-derived "the findings for this PR" from raw review data: `PRRow`'s hover-popup content and `FindingsTab`'s page-level aggregate counter. Both still used the OLD single-latest-review logic, so the popup showed "No findings" while the (now-correct) badge count showed real numbers — a real user-visible bug from touching only the server side of a semantic change. Fixed by extracting one shared `latestReviewPerAgent()` helper (`pulls/helpers.ts`) and using it in both places instead of leaving each to reimplement the same "which review(s) count" logic.
- _2026-07-30_ — **`?? 0` before summing two nullable numeric inputs hides "missing" as "zero"** — `RunCostBadge`'s detailed variant (`src/components/run-cost/RunCostBadge.tsx`) computed `(tokensIn ?? 0) + (tokensOut ?? 0)` and displayed "0 tok" for runs with no recorded token data, indistinguishable from a run that genuinely used zero tokens. Fix: check both inputs for `null`/`undefined` explicitly (`tokensIn != null && tokensOut != null ? tokensIn + tokensOut : null`) and render a placeholder (`"—"`) when either is absent, rather than defaulting to 0 before the null-check. Applies to any display code combining nullable numeric fields — `?? 0` is fine for arithmetic accumulators that get used further, wrong for anything rendered straight to the user.

## Codebase Patterns

- _2026-08-08_ — **`MonoLink` (`vendor/ui/primitives/MonoLink.tsx`) renders an inert, focusable `<button onClick={undefined}>` — not plain text — whenever `href` is falsy, and this is a separate gap from the `title`-prop one logged just below** — `MonoLink.tsx:47-58`'s fallthrough always returns a `<button>`, so a caller that conditionally omits `href` (e.g. because `repoFullName`/`headSha` aren't resolved yet) gets a dead, hoverable/focusable control unless it branches around `MonoLink` itself. Blast-tab's line-level references (`specs/0007-blast-radius-ux-fixes.md` §0) needed a real text fallback in that case, so a small local wrapper (`LineRef` in `BlastTab.tsx`, not promoted anywhere — single consumer) checks `href` first and renders a plain `<span>` when it's absent, falling through to `<MonoLink href={href}>` only when a link is possible. Any future consumer of `MonoLink` with an optional/nullable `href` needs the same guard — do not assume "no href" degrades gracefully to text on its own.
- _2026-08-08_ — **`MonoLink` (`vendor/ui/primitives/MonoLink.tsx`) had no `title` prop before the Blast-tab in-diff-jump feature (`specs/0006-blast-radius-polish.md` §3a), even though the design decision calling for it (a `title`/`aria-label` distinguishing the same-page-navigation button from the external-link affordance, §5) assumed one existed** — added `title?: string`, forwarded to both the `<a>` and `<button>` branches, as a small backward-compatible extension (optional prop, no behavior change for any existing caller). Any future plan/spec that shows example JSX passing a prop to a vendored `@devdigest/ui` primitive should be treated as "verify the prop exists first" — `MonoLink`'s actual shape at the time didn't match the plan's snippet, and the fix was additive rather than a sign the plan was wrong.
- _2026-08-05_ — **A per-item deep-link into a tab that gets unmounted must have its target state owned by an ancestor that survives the tab switch — this is now a two-time pattern** — the existing run-level Timeline→accordion scroll (`targetRunId`/`targetNonce`) lives inside `FindingsTab.tsx` because both the trigger (`RunHistory`) and the destination (`ReviewRunAccordion`) are mounted together there. The Smart Diff finding-marker → Agent-runs-tab navigation (L03) could NOT follow that shape: the trigger (`DiffTab`, on the Files-changed tab) and the destination (`FindingsTab`, on the Agent-runs tab) are DIFFERENT tabs, and `page.tsx` only mounts one tab's content at a time (`tab === "findings" && <FindingsTab/>`). Putting the target state inside `FindingsTab` would lose it the instant the tab switched and unmounted the setter. Fixed by owning `findingTarget` in `page.tsx` itself — the one component that stays mounted across a `?tab=` change on the same route (`page.tsx` → `FindingsTab` → `ReviewRunAccordion` → `FindingsPanel`, mirroring `targetRunId` one level deeper). Any future CROSS-TAB (not just cross-component) deep-link in this app needs the same placement: state on the nearest ancestor that outlives BOTH the trigger and the destination, not just the destination.
- _2026-08-05_ — **A third confirmed instance of "pre-built, unused i18n scaffolding waiting for its lesson"** — `messages/en/prReview.json`'s `smartDiff.*` block (`coreLabel`/`wiringLabel`/`boilerplateLabel`/`largeTitle`/`largeBody`/`filesCount`/`findingLines`/`groupedByRole`) existed with zero consumers before the Smart Diff feature (L03) was implemented, the same pattern already logged for `pulls/status.ts`'s `rollupSeverities` and the `reviews` module's pre-existing `upsertIntent`/`getIntent` pair (`server/insights.md`, 2026-07-30 / 2026-08-05). Reused as-is; only `findingLines`'s English value needed to change (`"{count} finding-lines"` → `"{count} findings"`). Before adding new copy for a course-lesson feature, grep the relevant `messages/en/*.json` file for a plausible key first — it is often already there, pre-built ahead of the lesson that consumes it.
- _2026-08-05_ — **`client/src/vendor/shared/adapters.ts` is NOT a byte-for-byte mirror of `server/src/vendor/shared/adapters.ts`** — the client's copy is missing several members the server's has (e.g. `GitClient.sync`/`diffNameOnly`, `GitHubClient.commitFiles`/`findOpenPr`, `StructuredRequest.sessionId`), presumably because the client only ever needed a subset historically. When adding a NEW adapter interface (e.g. `WebFetchClient` for L03) that both copies must carry, diff just the new block you're adding between the two files — don't assume "keep the copies identical" means the whole file is otherwise in sync, it isn't.
- _2026-08-04_ — **A mocked `next/navigation` router that mutates a module-level variable does NOT trigger a React re-render on its own** — `SkillsView.test.tsx` (and the earlier version of it) mocks `useRouter().replace` to write into a module-level `URLSearchParams`, and `useSearchParams()` reads that same variable. Firing a click that calls `replace()` updates the variable immediately, but the component that already rendered has no way to know — React only re-renders from state/props/context changes, and a plain module variable is none of those. Symptom: `waitFor(() => expect(screen.getByText(...)).toBeInTheDocument())` times out even though the assertion "should" eventually be true, because nothing ever re-renders to make it true. Fix: after any action that depends on the mocked `replace()` taking effect, explicitly force a fresh render (`cleanup(); renderView();` — see `renderAfterNavigation()`) rather than waiting. This is not a new problem introduced by the Skills work — the original `SkillsView.test.tsx` already worked around it for its one selection test; the redesign just added several more assertions (tab switching) that needed the same treatment.
- _2026-08-04_ — **A drag-reorder list needs an optimistic mutation, and `cancelQueries` is the non-obvious half of it** — `useSetAgentSkills` (`src/lib/hooks/agents.ts`) is the only optimistic hook in the app; every other mutation invalidates on success. Without `onMutate` a dragged row snaps back to the server order for a whole round-trip, which reads as "the drag didn't work". The part that is easy to omit: `await qc.cancelQueries({ queryKey: [...] })` FIRST — an already-in-flight GET that resolves after the optimistic `setQueryData` overwrites it with the pre-drag order, producing an intermittent revert that looks like a server bug. `SkillsTab.test.tsx` pins this by holding the POST promise open and asserting the new row order renders while it is still pending.
- _2026-08-04_ — **Reordering from a filtered list silently drops the hidden items** — the agent Skills tab persists the FULL ordered id array (`POST /agents/:id/skills { skill_ids }`), so a drag performed while a filter hides some linked skills would write only the visible subset and detach the rest. Dragging is disabled outright while the filter box is non-empty (`SkillsTab.tsx`, with a hint swap) rather than trying to splice the visible subsequence back into the full list. Any future "reorder a filtered list" UI in this app has the same trap.
- _2026-07-30_ — **A component shared between the PR-list route and the PR-detail (`[number]`) route lives under `pulls/_components/`, not `@devdigest/ui`** — `SeverityCounts` (severity readout used by both `PRRow` in the list and `RunHistory`/`FindingsTab` on the detail page) is colocated at `pulls/_components/SeverityCounts/`, imported from the detail side via a relative path up through `[number]/_components/` (e.g. `../../../_components/SeverityCounts` from `pulls/[number]/_components/RunHistory/`). Kept out of `@devdigest/ui` deliberately since it's specific to the findings/severity domain, not a generic UI primitive — promote it there only if a third, unrelated consumer shows up.
- _2026-07-30_ — **A TanStack Query hook can be made "fetch only while hovered" by adding an `{ enabled }` option, reusing the SAME hook/endpoint another page already calls** — `usePrReviews(prId, { enabled })` (`src/lib/hooks/reviews.ts`) is the same hook the PR-detail page already uses for its full findings list; `PRRow` on the PR-list page calls it too, gated on `enabled: popupHover`, to lazily fetch one row's findings only when its FINDINGS-column popup is actually hovered — no separate lazy-fetch hook needed, and react-query's cache makes re-hovering the same row instant after the first fetch.

## Tool & Library Notes

- _2026-08-08_ — **`@testing-library/user-event` is NOT an installed dependency in `client/`** — it's absent from `package.json` and `node_modules/@testing-library/` (only `react` and `jest-dom` are present), despite the `react-testing-library` skill's default guidance to always use it over `fireEvent`. `DiffTab.test.tsx`'s pre-existing click test already uses `fireEvent.click(...)`, which is this codebase's actual (if not skill-preferred) convention. When writing a NEW interaction test in `client/`, check `node_modules/@testing-library/user-event` exists before importing it — if it doesn't, use `fireEvent` to match the rest of the suite rather than silently adding a new dependency (`pnpm add -D`) as a drive-by inside an unrelated feature change.
- _2026-08-04_ — **react-markdown v9's `code` component override fires for BOTH inline code and fenced-block code with no `inline` prop to distinguish them (that prop was removed after v6), and an inline `style` attribute can never be beaten by a CSS rule, no matter the selector** — `Markdown.tsx`'s single `code` override applied inline-chip styling (small `border-radius`, `background`, `padding: "1px 6px"`) unconditionally to every `<code>`; `styles.css`'s `.dd-md pre code { background: none; padding: 0 }` was written to cancel that out for fenced blocks but structurally can't, since inline `style=""` always wins over any class selector regardless of specificity. Symptom: a fenced code block rendered as two mismatched nested rounded boxes (the block's own `.dd-md pre` background+radius, plus the chip's smaller one inside it) — reads visually as "broken"/cut-off corners. Fix: override `pre` separately in the `components` map, extract the already-rendered `code` child's raw text (`children.props.children`), and re-render a plain `<pre><code>{text}</code></pre>` with NO inline styles, letting `.dd-md pre` / `.dd-md pre code` (CSS) own the block's look entirely — react-markdown only routes a fenced block's `code` node through the separate `pre` override once one exists, so the original `code` override becomes reachable only for genuine inline code.
- _2026-08-04_ — **Customizing `::-webkit-scrollbar-thumb`/`-track` without also setting `::-webkit-scrollbar-corner` leaves a stray white/light square wherever an element scrolls in BOTH directions at once** — `SkillBodyEditor`'s textarea (`overflowX: auto; overflowY: auto`) shows a horizontal scrollbar on long unwrapped lines; the corner square where it meets the vertical scrollbar defaulted to the browser's own light color since no rule targeted it, reading as a stray white triangle against the dark theme. Fixed globally in `vendor/ui/styles.css`, right next to the existing thumb/track rules, rather than per-component — any future element that scrolls both ways inherits the fix automatically.
- _2026-08-04_ — **This sandbox's Browser pane does not composite frames, so `document.body.innerText` (and the `get_page_text`/screenshot tools built on rendered layout) can report EMPTY or stale content even though the real DOM is fully populated** — `innerText` requires layout to have run; `textContent` does not, and reliably reflects the live DOM regardless of compositing state. When verifying a client change in this environment, read `document.querySelector(...).textContent` (or `.innerHTML`) via `javascript_tool` instead of `get_page_text` / `computer screenshot`, and don't treat an apparently-blank page as evidence of an app bug without checking `textContent` first. Separately: repeatedly stopping/restarting the dev server while reusing the same browser tab across many HMR cycles in one long session can leave the page stuck showing loading skeletons forever with no console error — confirmed reproducible on an untouched, pre-existing route too, so it's tooling/session churn, not app code. A full server restart AND a brand-new tab (`tabs_create`) together resolve it; either alone did not.
- _2026-08-04_ — **Tailwind's Preflight (`@import "tailwindcss"`, `styles.css:1`) combines with this repo's OWN `h1,h2,h3,h4,p { margin: 0 }` reset (`styles.css:205-211`) to make ALL rendered markdown look like flat, unstyled body text app-wide** — Preflight already strips heading font-size/weight and list `list-style`/`padding-left` to zero; the repo's reset then also zeroes heading/paragraph margins on top. `Markdown.tsx` (`vendor/ui/primitives/Markdown.tsx`) only overrides `p`/`strong`/`code`/`a` and emits `className="dd-md"` on its wrapper, but **no `.dd-md` CSS rule existed anywhere** — so every consumer (skill body preview, import preview, anywhere `<Markdown>` is used) rendered `## Heading` and `- item` as plain paragraphs with no bullet. Not a bug in any one feature; it's a hole in the shared primitive that every future consumer inherits silently. Fixed by adding a `.dd-md` block to `vendor/ui/styles.css` that explicitly RE-establishes heading sizes/weights/margins and `ul`/`ol` `list-style`+`padding-left` (plus `li>p{margin:0}`, since react-markdown wraps loose list items in `<p>` which would otherwise inherit the 10px bottom margin from `Markdown.tsx`'s own `p` override and blow list spacing apart). Before touching `Markdown.tsx`'s `components` overrides for a NEW element type, check whether `.dd-md` in `styles.css` already needs it instead — CSS is the right layer for anything that isn't per-element JS logic (first-child margin, nested list spacing).
- _2026-08-04_ — **Hand-rolled HTML5 drag-and-drop has three failure modes that all look like "drag is broken"** (`src/lib/drag-list.ts`, written this way because the app carries no DnD dependency): `onDragOver` MUST call `preventDefault()` or the drop event never fires at all; `dataTransfer.setData(...)` must be called in `onDragStart` or Firefox refuses to begin the drag; and `dataTransfer.getData()` is unreadable during `dragover` in most browsers, so the dragged id has to be tracked in component state rather than round-tripped through the event. In jsdom tests, `fireEvent.dragStart/dragOver/drop` do not synthesise a `dataTransfer` at all — pass a stub (`{ setData, getData, effectAllowed, dropEffect }`) in the event init or the handlers throw.
- _2026-07-30_ — **Setting only `overflowY: "auto"` on a fixed-width box lets unbreakable text force a horizontal scrollbar** — per the CSS overflow spec, when one axis is set to something other than `visible` and the other is left at the default `visible`, the `visible` one computes to `auto` too. `SeverityCounts`' popup (`overflowY: "auto"`, `maxWidth: 360`, no explicit `overflowX`) grew a horizontal scrollbar whenever a finding's file path (no spaces to wrap on) was long. Fix: set `overflowX: "hidden"` explicitly as a hard backstop, AND add `overflowWrap: "anywhere"` / `wordBreak: "break-word"` / `flexWrap: "wrap"` to the row holding the path so it actually wraps instead of being invisibly clipped. Overflow-hidden alone would silently cut the text off — both halves of the fix are needed.

## Recurring Errors & Fixes

- _2026-08-07_ — **`overrides.x ?? DEFAULT` silently discards an explicit `null` override in a test render-helper, because `??` treats `null` and `undefined` identically** — `BlastTab.test.tsx`'s `renderTab({ repoFullName: null })` was meant to force the "unknown repo" case, but the helper computed `overrides.repoFullName ?? REPO_FULL_NAME`; since the passed-in `null` is nullish, `??` fell through to the non-null default, so the "no link when `repoFullName` is null" test actually rendered WITH a real `repoFullName` and asserted on a link that shouldn't have existed (only caught because the assertion failed loudly, not silently). Any test helper whose whole point is to let a caller override a value to `null` must use default-PARAMETER destructuring (`{ repoFullName = DEFAULT }: { repoFullName?: X | null }`) instead of `??` inside the body — parameter defaults only fire on `undefined`, never on an explicitly-passed `null`, which is exactly the distinction needed here.
- _2026-08-07_ — **A grep-based "no raw `fetch(` outside the hook" static guard has a false-positive on TanStack Query's own `refetch()`** — `grep -rn "fetch(" <folder>` (used in `specs/0005-blast-radius.md`'s verification steps and worth reusing for any future feature folder) matches the substring `fetch(` inside `refetch(`, which is the query result's own reload callback, not a network call. `BlastTab.tsx` destructures it as `{ refetch: reload }` specifically so the guard greps clean — do the same rename in any component that both (a) lives under a folder covered by this exact grep pattern and (b) calls a query's `refetch()` for a retry button, rather than leaving the false positive for someone to puzzle over later.
- _2026-08-07_ — **`borderColor` is itself a shorthand — pairing it with `borderLeftColor` in one inline-style object trips React's "conflicting property" warning, even though `border` was already avoided** — `FindingCard/styles.ts` carried a comment reading "never mix `border` shorthand with `borderLeft`" and used `borderStyle`/`borderColor`/`borderWidth`/`borderLeftWidth`/`borderLeftColor`, which looks all-longhand but isn't: `borderColor` expands to the four per-side colors, one of which `borderLeftColor` then overrides. React only warns when the shorthand's VALUE CHANGES on a rerender, so this stayed invisible until something toggled it — here `focused`, flipping as a Smart Diff marker navigated to the card, which made it read as an intermittent navigation bug rather than a static style problem. Fix: write `borderTopColor`/`borderRightColor`/`borderBottomColor` explicitly and leave the left side to `borderLeftColor`. The same latent pair existed in `conventions/_components/ConventionCard/styles.ts` (keyed on `status`) and was fixed alongside. When a per-side override is needed, no `border*` group property is safe — only the true per-side longhands are.
- _2026-08-04_ — **`Modal` (`vendor/ui/kit/Modal.tsx`) applies ZERO padding to its children — every caller must supply its own padded wrapper, or content sits flush against the modal edges** — unlike `Drawer` (`vendor/ui/kit/Drawer.tsx`), which bakes `padding: 24` into its own children wrapper, `Modal`'s content div is only `{ flex: 1, overflow: "auto" }`, no padding at all. `CreateAgentModal` gets this right (`<div style={s.body}>`, `padding: 24`, its own `styles.ts`) but `CreateSkillModal` (pre-existing, `app/skills/_components/CreateSkillModal/`) and a new Conventions-merge-to-skill modal both originally shipped without the wrapper and rendered edge-to-edge with a "broken" look (reported independently twice — once per modal). Before adding any new `<Modal>` consumer, add a `padding: 24` wrapper div around its children by default — `Modal` will never do it for you.

- _2026-08-08_ — **A scroll-target `useEffect` living on the destination card itself is not a stable enough lifecycle when its ancestor swaps subtrees mid-load** — `FileCard`'s original blast-radius "jump to file" implementation (`specs/0006-blast-radius-polish.md` §3c) scheduled `scrollIntoView` from `FileCard`'s own effect (deferred two `requestAnimationFrame`s to let `setOpen(true)` paint first). It never fired: `DiffTab` renders the flat `DiffViewer` fallback while `usePrSmartDiff` is loading, then swaps to `SmartDiffViewer` once it resolves — a full subtree replacement, not a re-render — so the target `FileCard` mounts, its effect schedules the deferred scroll, and the swap unmounts it (running the cleanup, cancelling the scheduled frames) before they fire; this repeated across the swap's several remounts (confirmed live: 4 "effect fired"→"cleanup" pairs within ~250ms, zero of the two rAF callbacks ever ran). Fix: own the scroll from `DiffTab` instead — it never remounts across that swap, only its rendered output changes — via a self-terminating poll (`setTimeout`, capped attempts) that waits for `document.getElementById(targetId)` to exist with a non-zero rect; `FileCard`'s own effect now only force-opens (`setOpen(true)`), which is idempotent and safe to rerun on every one of its remounts. General lesson: a scroll/focus/animation effect that depends on "the target DOM node existing and being laid out" belongs on the nearest ancestor that is guaranteed not to unmount across the transition that produces that node, not on the node's own component.
- _2026-08-08_ — **`requestAnimationFrame` callbacks can silently never fire in this project's browser-automation testing tool** when its pane reports "not displayed, so the page is not compositing frames" (the same message `computer.screenshot` gives when the pane isn't visible) — confirmed by instrumenting a `useEffect`'s rAF chain: the effect body itself ran (logged), but neither the first nor a chained second `requestAnimationFrame` callback ever logged, even after several seconds. Rewriting the same wait as `setTimeout` fired immediately. Two implications: (1) prefer `setTimeout` over `requestAnimationFrame` for a "wait a tick then check the DOM" pattern in code that must also work headless/non-composited, not just for real foregrounded tabs; (2) **`Element.scrollIntoView({ behavior: "smooth" })` also silently never completes in a non-composited tab** (smooth-scroll is compositor-driven) — `{ behavior: "instant" }` applies immediately regardless. When verifying a `scrollIntoView`-based feature through this tool and the scroll position doesn't move even though your code logs that it called `scrollIntoView`, this is very likely why — don't conclude the feature is broken from that alone; substitute `instant` locally to confirm the target/position logic is correct, then trust `smooth` for real users (a real, foregrounded browser tab composites normally). Ship `smooth` when matching an existing convention (e.g. `FindingsPanel`'s own scroll-to-finding already uses it) — the non-completion is a property of this specific test harness, not of real browsers.
