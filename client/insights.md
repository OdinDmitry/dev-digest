## What Works

- _2026-08-17_ — **Resolved the `ContextAttachPanel` checkbox-focusability defect (2026-08-17 Open Question below) by giving the checkbox `<span>` its OWN `tabIndex={0}` and leaving the row `<div>`'s `tabIndex={0}` in place, rather than moving the Tab stop off the row entirely** — the plan (`docs/plans/2026-08-17-context-attach-row-role-a11y.md`) offered two shapes: single-tab-stop-per-row (move `tabIndex` from the row onto the checkbox, repoint `rowRefs`) or this minimal one. The single-tab-stop option looks cleaner but breaks `getRow()` in `ContextAttachPanel.test.tsx` (`screen.getByText(path).closest('[tabindex="0"]')`) for every test that focuses "the row" (`moves a focused row…`, `does not permit reordering…`, `marks an attachment absent…`) — the text span is a sibling of the checkbox, not a descendant, so `.closest()` finds nothing once the row itself loses its `tabIndex`. Since `rowRefs`-based focus retention after `Alt+Arrow` also targets the row, keeping the row's own `tabIndex` was required to avoid touching test selectors that belong to `test-writer`. Net: two Tab stops per row on the state toggle (row, then checkbox) instead of one — a real a11y regression on tab-surface size versus the "recommended" option, accepted here to keep the reorder path and its existing tests untouched. If this component's tests are ever retargeted to query controls purely by role (no `getRow()`/`.closest('[tabindex="0"]')` selector), revisit and switch to the single-tab-stop shape.
- _2026-08-16_ — **Fixed `useSetOwnerContext`'s attach-side `token_count: 0` placeholder (see Open Questions 2026-08-16) by reading the real count from the documents-listing cache** — `hooks/context.ts`'s `onMutate` now does `qc.getQueryData<ContextListing>(["context", "documents", repoId])` and builds a `path → token_count` map from it; any `path` missing from `prev.attachments` (i.e. just toggled ON) now looks up its real count there instead of defaulting to `0`, falling back to `0` only if the listing cache itself has no entry (e.g. not yet fetched). `ContextAttachPanel.test.tsx`'s combined-count test (previously red on the attach half) is now green; detach/reorder behavior (which already worked) is unchanged since those paths still come from `prev.attachments` via `byPath`.

## What Doesn't Work

- _2026-07-30_ — **Portaling a hover-popup to `<body>` (to escape an ancestor's `overflow: hidden`) breaks the usual "parent `onMouseEnter`/`onMouseLeave`" hover pattern** — once the popup is `createPortal`'d out to `document.body`, it's no longer a DOM descendant of the trigger, so an instant `setHovering(false)` on the trigger's `onMouseLeave` unmounts the popup before the mouse has actually reached it (the browser's leave-before-enter event ordering means the popup can vanish mid-transition, with no element left to catch its `mouseenter`). Adding matching `onMouseEnter`/`onMouseLeave` to the popup itself is necessary but NOT sufficient. Fix: debounce the close (`setTimeout(~120ms)` in the leave handler) and cancel it from either element's `onMouseEnter` — see `SeverityCounts.tsx`. Any future portaled hover-UI in this app needs the same debounce, not just mirrored handlers.
- _2026-07-30_ — **When a server aggregation's SEMANTICS change, grep the client for every independent re-derivation of the same metric** — changed the PR-list route's findings/cost aggregation from "latest review overall" to "latest review per agent, summed" (see server `insights.md`), but two client-side spots independently re-derived "the findings for this PR" from raw review data: `PRRow`'s hover-popup content and `FindingsTab`'s page-level aggregate counter. Both still used the OLD single-latest-review logic, so the popup showed "No findings" while the (now-correct) badge count showed real numbers — a real user-visible bug from touching only the server side of a semantic change. Fixed by extracting one shared `latestReviewPerAgent()` helper (`pulls/helpers.ts`) and using it in both places instead of leaving each to reimplement the same "which review(s) count" logic.
- _2026-07-30_ — **`?? 0` before summing two nullable numeric inputs hides "missing" as "zero"** — `RunCostBadge`'s detailed variant (`src/components/run-cost/RunCostBadge.tsx`) computed `(tokensIn ?? 0) + (tokensOut ?? 0)` and displayed "0 tok" for runs with no recorded token data, indistinguishable from a run that genuinely used zero tokens. Fix: check both inputs for `null`/`undefined` explicitly (`tokensIn != null && tokensOut != null ? tokensIn + tokensOut : null`) and render a placeholder (`"—"`) when either is absent, rather than defaulting to 0 before the null-check. Applies to any display code combining nullable numeric fields — `?? 0` is fine for arithmetic accumulators that get used further, wrong for anything rendered straight to the user.

## Codebase Patterns

- _2026-08-22_ — **`useFocusTrap` needs a ref to a container that contains EVERYTHING focusable in the dialog, including `Modal`'s own header close button — since `Modal.tsx` accepts no `ref`/`containerRef` prop and must not be modified (client/insights.md 2026-08-04 below, plus this session's Track B handoff clarification 1), the trap ref has to wrap the WHOLE `<Modal>` element from outside, not just its `children`.** `CompareRunsDialog.tsx` renders `<div ref={dialogRef}><Modal ...>{...}</Modal></div>` and calls `useFocusTrap(dialogRef, true, onClose)` on that outer div — `Modal`'s root is `position: fixed`, so wrapping it in a plain non-positioned div changes nothing visually, but `getFocusable()`'s `querySelectorAll` now sees the header's `IconBtn` X button, the body content, and the footer buttons all as descendants of one container, so Tab cycles through the full dialog (X button included) instead of skipping it. Any future `Modal` consumer that needs `useFocusTrap` (the eval-case dialog is the other one AC-43/AC-44 name) should reuse this same "wrap the whole `<Modal>`, not just its children" shape rather than trying to ref just the children wrapper.
- _2026-08-22_ — **`GET /agents/:id/eval-runs` (`useAgentEvalRuns`) returns every suite run for the agent — pending/running/completed/failed, newest-first — not just `state === 'completed'` runs, even though AC-36's text says "present that agent's completed suite runs."** Confirmed by reading `server/src/modules/evals/repository/run.repo.ts`'s `listRunsForAgent` (no `state` filter) and `service.ts#listRuns` (maps every row, no filter either). Read together with T13's own task text (a *failed* run must render `dashboard.runFailed`, which is impossible if failed runs were excluded), the intended client behavior is: filter the array to the two TERMINAL states (`completed` OR `failed`) for the history table — drop `pending`/`running` (an in-progress run is surfaced elsewhere, via `useActiveEvalRun`'s poll, not as a row here) — then branch presentation per row on `state`. `RunHistoryTable.tsx` does exactly this (`runs.filter(r => r.state === "completed" || r.state === "failed")`). Don't assume the array itself is pre-filtered to "completed" the way AC-36's literal wording suggests.
- _2026-08-22_ — **`EvalRunRecord.delta` (recall/precision/citation_accuracy/cost_usd, each nullable) is already computed server-side against "the immediately preceding COMPLETED run of the same agent" (AC-38) — the client must render it, never recompute it from consecutive array entries.** `service.ts#listRuns` computes `earlier = rows.slice(i+1).find(r => r.state === 'completed')` per row BEFORE any client-side filtering happens, so a failed run sitting between two completed runs in the raw array does not break the delta chain — filtering the array client-side (see the entry above) to drop pending/running rows is safe precisely because delta was computed against the unfiltered order server-side, not against whatever subset ends up on screen. `RunHistoryTable.tsx`'s `MetricCell` just reads `run.delta?.recall` etc. and formats it (`Math.round(Math.abs(delta) * 100)}pts"` for the three rate metrics, `formatCost` for cost) — the same `EvalComparisonMetric.delta` shape is reused as-is by `CompareRunsDialog.tsx`'s `MetricBox` for AC-40's earlier→later boxes, again with no client recomputation.

- _2026-08-22_ — **A polling query that must "invalidate sibling caches exactly once when it transitions into a terminal state" needs a `useEffect` + `useRef` pair alongside the `useQuery`, not just a `refetchInterval` callback** — `hooks/evals.ts`'s `useActiveEvalRun`/`useEvalRun` (SPEC-03 AC-24/AC-26) poll every 1.5s via `refetchInterval: (q) => isTerminal(q.state.data) ? false : 1500`, but `refetchInterval` only controls WHETHER to schedule the next fetch — it has no hook for "this fetch just made the state cross from running into completed/failed, do something once". Implemented as a `wasTerminal` ref initialized to `true` (so mount with no active run doesn't fire) plus a `useEffect([query.data, ...])` that compares the ref against the freshly computed `isTerminal(query.data)` and calls `qc.invalidateQueries` on the `!prev && now` edge only, then updates the ref. `isTerminal` treats `undefined` (not-yet-fetched, or `data` reset by a `queryKey` change) as NOT terminal specifically to avoid a false transition-into-terminal firing spurious invalidation the instant `agentId`/`runId` changes and react-query clears `data` back to `undefined`. Any future "poll until X, then refresh Y" hook in this app should reuse this ref-based edge-detection shape rather than trying to derive it from `refetchInterval` alone.
- _2026-08-22_ — **`useFocusTrap`'s effect intentionally omits `onClose` from its dependency array (only `[active, ref]`), storing it in a ref updated every render instead** — an inline `onClose={() => setOpen(false)}` passed from a dialog is a new function identity every render; if the effect depended on it directly, every parent re-render while the dialog was open would tear down and re-run the whole open/focus/listener setup, re-stealing focus onto the first focusable element out from under the user. `use-focus-trap.ts` keeps `onCloseRef.current = onClose` as a plain assignment on every render (no effect needed for that part) and only the Escape handler reads `onCloseRef.current()`, so the trap setup/teardown is driven purely by `active` toggling. Any future hook taking a caller-supplied callback that must be "always current" without retriggering the hook's own setup effect should use the same ref-mirroring shape.
- _2026-08-17_ — **A hand-built `RunTrace` object literal in a client test fixture breaks at RUNTIME (not just typecheck) the moment a new required field is added to the shared `RunTrace` Zod contract, because `RunTrace.parse()` is never called client-side** — `RunTraceDrawer.test.tsx`'s `baseTrace` fixture was missing `specs_excluded` after `contracts/trace.ts` added `specs_excluded: z.array(ContextExclusion).default([])` (`docs/plans/2026-08-16-project-context-run-injection.md`, U1/U2). Client `pnpm typecheck` catches this (TS2741, since `.default()` makes the field required in `z.infer`'s output type — same rule already logged in `server/insights.md` 2026-07-30) but the WORSE symptom is `pnpm test:unit`: `TraceBody.tsx` reads `trace.specs_excluded.length` unconditionally (mirroring the existing `specs_read.length` Row), so the fixture's `undefined` throws `Cannot read properties of undefined (reading 'length')` at render time, not a clean assertion failure. Any future field added to `RunTrace`/`RunStats`/`PromptAssembly` needs the SAME fixture update in `RunTraceDrawer.test.tsx` (and any other hand-built trace fixture) — grep the client for `specs_read:` or the contract's other required keys to find every literal fixture before assuming the shared-contract change is "just a server thing".

- _2026-08-17_ — **ARIA's presentational-children rule (children of `role="checkbox"` are permitted to be hidden from AT entirely) means a composite row that needs BOTH a checked-state indicator AND independently focusable controls (a preview button, a reorder handle) cannot put `role="checkbox"` on the row itself if those controls live inside it** — `ContextAttachPanel.tsx`'s row previously put `role="checkbox"`/`aria-checked`/the `attachAria` name on the outer row `<div>`, with a real `<button>` (preview) and a `role="img"` grip nested inside; per the rule, AT could legally expose neither. Fixed by moving `role="checkbox"`/`aria-checked`/`attachAria` down onto the small leaf indicator span (the visual checkmark box, whose only child is a decorative icon) instead of the row — a leaf has no interactive descendants, so the rule no longer applies, and the row stays a plain focusable container that still owns the actual toggle (`onClick`/Enter-Space) and reorder (`Alt+Arrow`) interactions via its own handlers. Any future "row represents one togglable state but also contains other actionable children" component in this app needs the same split: role/state/name on the leaf state-indicator, interaction handlers stay on the row.
- _2026-08-17_ — **A drag-handle promoted from `role="img"` to a real `<button>` nested inside a row that owns `Alt+Arrow` reorder keydown handling does not need its own reorder logic — the keydown bubbles from the button up to the row's existing handler for free** — `ContextAttachPanel.tsx`'s grip button has no `onKeyDown` of its own; React attaches the row's `onKeyDown` via normal DOM bubbling, so `Alt+ArrowUp/Down` fired while the grip button has focus still reaches the row's handler unchanged. The button's `onClick` only needs `e.stopPropagation()` (to stop the row's own `onClick` from toggling attach when the grip is clicked) and a `disabled={!draggable}` to match `AC-14`'s "no reorder while filtering" gate — no direction-specific click behavior was needed to satisfy "the grip performs the same move as `Alt+Arrow`".
- _2026-08-16_ — **`VALID_TABS` in a sibling list-view's constants.ts silently swallows a new detail-pane tab key added elsewhere** — adding `"context"` to `SkillDetail/constants.ts`'s `TABS` was not enough on its own: `SkillsView.tsx` validates `?tab=` against a SEPARATE `VALID_TABS` array in `SkillsView/constants.ts` and falls back to `"config"` for anything not in it, so `?tab=context` would silently reset on reload/deep-link without also adding `"context"` to that array. The two lists (`SkillDetail`'s `TABS` for rendering, `SkillsView`'s `VALID_TABS` for URL validation) are not derived from each other — check both when adding a detail-pane tab.
- _2026-08-16_ — **A tab whose `labelKey` needs to resolve in a DIFFERENT next-intl namespace than the rest of its tab list can't use the single shared `t(tb.labelKey)` call** — `SkillDetail.tsx`'s `TABS` (config/context/preview/versions) share one `useTranslations("skills")` call, but the new Context tab's copy lives in `messages/en/context.json` (shared with the agent editor's identical tab, and with `ContextAttachPanel` itself) rather than duplicated into `skills.json`. Fixed by adding a second `const tc = useTranslations("context")` and special-casing `tb.key === "context"` in the `tabs.map()` that builds the `<Tabs>` prop, instead of making `labelKey` resolution namespace-aware generically. Any future cross-namespace tab entry in an existing `TABS` array needs the same one-off special case.
- _2026-08-08_ — **`MonoLink` (`vendor/ui/primitives/MonoLink.tsx`) renders an inert, focusable `<button onClick={undefined}>` — not plain text — whenever `href` is falsy, and this is a separate gap from the `title`-prop one logged just below** — `MonoLink.tsx:47-58`'s fallthrough always returns a `<button>`, so a caller that conditionally omits `href` (e.g. because `repoFullName`/`headSha` aren't resolved yet) gets a dead, hoverable/focusable control unless it branches around `MonoLink` itself. - _2026-08-08_ — **`MonoLink` (`vendor/ui/primitives/MonoLink.tsx`) had no `title` prop before the Blast-tab in-diff-jump feature (`specs/0006-blast-radius-polish.md` §3a), even though the design decision calling for it (a `title`/`aria-label` distinguishing the same-page-navigation button from the external-link affordance, §5) assumed one existed** — added `title?: string`, forwarded to both the `<a>` and `<button>` branches, as a small backward-compatible extension (optional prop, no behavior change for any existing caller). - _2026-08-05_ — **A per-item deep-link into a tab that gets unmounted must have its target state owned by an ancestor that survives the tab switch — this is now a two-time pattern** — the existing run-level Timeline→accordion scroll (`targetRunId`/`targetNonce`) lives inside `FindingsTab.tsx` because both the trigger (`RunHistory`) and the destination (`ReviewRunAccordion`) are mounted together there. - _2026-08-04_ — **A mocked `next/navigation` router that mutates a module-level variable does NOT trigger a React re-render on its own** — `SkillsView.test.tsx` (and the earlier version of it) mocks `useRouter().replace` to write into a module-level `URLSearchParams`, and `useSearchParams()` reads that same variable. Firing a click that calls `replace()` updates the variable immediately, but the component that already rendered has no way to know — React only re-renders from state/props/context changes, and a plain module variable is none of those. Symptom: `waitFor(() => expect(screen.getByText(...)).toBeInTheDocument())` times out even though the assertion "should" eventually be true, because nothing ever re-renders to make it true. - _2026-08-04_ — **A drag-reorder list needs an optimistic mutation, and `cancelQueries` is the non-obvious half of it** — `useSetAgentSkills` (`src/lib/hooks/agents.ts`) is the only optimistic hook in the app; every other mutation invalidates on success. The part that is easy to omit: `await qc.cancelQueries({ queryKey: [...] })` FIRST — an already-in-flight GET that resolves after the optimistic `setQueryData` overwrites it with the pre-drag order, producing an intermittent revert that looks like a server bug. `SkillsTab.test.tsx` pins this by holding the POST promise open and asserting the new row order renders while it is still pending.

Dragging is disabled outright while the filter box is non-empty (`SkillsTab.tsx`, with a hint swap) rather than trying to splice the visible subsequence back into the full list. - _2026-07-30_ — **A component shared between the PR-list route and the PR-detail (`[number]`) route lives under `pulls/_components/`, not `@devdigest/ui`** — `SeverityCounts` (severity readout used by both `PRRow` in the list and `RunHistory`/`FindingsTab` on the detail page) is colocated at `pulls/_components/SeverityCounts/`, imported from the detail side via a relative path up through `[number]/_components/` (e.g. `../../../_components/SeverityCounts` from `pulls/[number]/_components/RunHistory/`). ## Tool & Library Notes

- _2026-08-22_ — **A `import { X } from "@devdigest/shared"` VALUE import (as opposed to `import type`) forces Next's webpack to actually resolve `src/vendor/shared/index.ts`'s barrel re-exports, and it can't — `tsc`/Vitest both silently rewrite the barrel's TS-style `.js` specifiers (e.g. `./contracts/knowledge.js`) to `.ts`, but Next's webpack does not (this repo's `next.config.ts` sets no `extensionAlias`), so `pnpm typecheck` and `pnpm test:unit` both stay green while `pnpm build` fails outright with `Module not found: Can't resolve './contracts/....js'` and every route 500s at runtime.** Hit when `EvalCaseDialog/helpers.ts` imported `EvalExpectation` as a value specifically to call `.safeParse()` on it client-side — the first (and, confirmed by grep, only) runtime use of a shared Zod schema anywhere in `client/src`; every one of the other ~89 `@devdigest/shared` imports in the client is already `import type`, which is erased before webpack ever sees it. Fix: keep the import `type`-only and hand-write a structural type guard (`typeof`/`Array.isArray`/`Number.isInteger` checks mirroring the Zod shape) instead of calling `.parse()`/`.safeParse()` on a vendored contract client-side — never add `extensionAlias` to `next.config.ts` to route around this, that's a repo-wide build-config change for what is really a "don't do runtime validation with the vendored barrel" convention. Any future client code that wants runtime validation against a shared contract needs the same hand-rolled-guard treatment, not a value import.
- _2026-08-22_ — **jsdom never runs layout, so `HTMLElement.offsetParent` is `null` for every element regardless of real visibility — a focus-trap's "get the focusable descendants" query must NOT filter by `offsetParent`, or it degenerates to "only the currently-focused element" in every test** — writing `use-focus-trap.ts`'s `getFocusable()`, the natural first draft filtered `querySelectorAll(FOCUSABLE_SELECTOR)` results by `el.offsetParent !== null` (a common real-browser "is it actually visible" check, since `display:none`/detached ancestors leave `offsetParent` null). In jsdom that predicate is false for literally every element except whichever one currently has focus (`el === document.activeElement`, which some implementations OR in as an escape hatch) — since jsdom does no layout, `offsetParent` is always `null`. Any focus-trap/roving-tabindex helper written against this codebase's vitest+jsdom suite needs a layout-free focusability check (just the CSS selector, trusting that a conditionally-rendered dialog is only in the DOM at all while genuinely visible) rather than `offsetParent`/`getBoundingClientRect`-based visibility filtering.
- _2026-08-08_ — **`@testing-library/user-event` is NOT an installed dependency in `client/`** — it's absent from `package.json` and `node_modules/@testing-library/` (only `react` and `jest-dom` are present), despite the `react-testing-library` skill's default guidance to always use it over `fireEvent`. `DiffTab.test.tsx`'s pre-existing click test already uses `fireEvent.click(...)`, which is this codebase's actual (if not skill-preferred) convention. When writing a NEW interaction test in `client/`, check `node_modules/@testing-library/user-event` exists before importing it — if it doesn't, use `fireEvent` to match the rest of the suite rather than silently adding a new dependency (`pnpm add -D`) as a drive-by inside an unrelated feature change.
- _2026-08-04_ — **react-markdown v9's `code` component override fires for BOTH inline code and fenced-block code with no `inline` prop to distinguish them (that prop was removed after v6), and an inline `style` attribute can never be beaten by a CSS rule, no matter the selector** — `Markdown.tsx`'s single `code` override applied inline-chip styling (small `border-radius`, `background`, `padding: "1px 6px"`) unconditionally to every `<code>`; `styles.css`'s `.dd-md pre code { background: none; padding: 0 }` was written to cancel that out for fenced blocks but structurally can't, since inline `style=""` always wins over any class selector regardless of specificity. Symptom: a fenced code block rendered as two mismatched nested rounded boxes (the block's own `.dd-md pre` background+radius, plus the chip's smaller one inside it) — reads visually as "broken"/cut-off corners. Fix: override `pre` separately in the `components` map, extract the already-rendered `code` child's raw text (`children.props.children`), and re-render a plain `<pre><code>{text}</code></pre>` with NO inline styles, letting `.dd-md pre` / `.dd-md pre code` (CSS) own the block's look entirely — react-markdown only routes a fenced block's `code` node through the separate `pre` override once one exists, so the original `code` override becomes reachable only for genuine inline code.
- _2026-08-04_ — **Customizing `::-webkit-scrollbar-thumb`/`-track` without also setting `::-webkit-scrollbar-corner` leaves a stray white/light square wherever an element scrolls in BOTH directions at once** — `SkillBodyEditor`'s textarea (`overflowX: auto; overflowY: auto`) shows a horizontal scrollbar on long unwrapped lines; the corner square where it meets the vertical scrollbar defaulted to the browser's own light color since no rule targeted it, reading as a stray white triangle against the dark theme. Fixed globally in `vendor/ui/styles.css`, right next to the existing thumb/track rules, rather than per-component — any future element that scrolls both ways inherits the fix automatically.

- _2026-08-18_ — **A `useMutation().mutate(...)` call does not invoke its `mutationFn` synchronously — asserting on a mocked `api.post` immediately after `fireEvent.click()`, in the same tick, sees zero calls even though the click handler ran.** Writing `BriefCard.test.tsx`'s regenerate test, `fireEvent.click(button); expect(post).toHaveBeenCalledWith(...)` failed with `Number of calls: 0`, even though a debug `console.log` right after the click confirmed exactly one matching `<button aria-label>` existed and the click dispatched. - _2026-08-07_ — **A grep-based "no raw `fetch(` outside the hook" static guard has a false-positive on TanStack Query's own `refetch()`** — `grep -rn "fetch(" <folder>` (used in `specs/0005-blast-radius.md`'s verification steps and worth reusing for any future feature folder) matches the substring `fetch(` inside `refetch(`, which is the query result's own reload callback, not a network call. `BlastTab.tsx` destructures it as `{ refetch: reload }` specifically so the guard greps clean — do the same rename in any component that both (a) lives under a folder covered by this exact grep pattern and (b) calls a query's `refetch()` for a retry button, rather than leaving the false positive for someone to puzzle over later.
- _2026-08-07_ — **`borderColor` is itself a shorthand — pairing it with `borderLeftColor` in one inline-style object trips React's "conflicting property" warning, even though `border` was already avoided** — `FindingCard/styles.ts` carried a comment reading "never mix `border` shorthand with `borderLeft`" and used `borderStyle`/`borderColor`/`borderWidth`/`borderLeftWidth`/`borderLeftColor`, which looks all-longhand but isn't: `borderColor` expands to the four per-side colors, one of which `borderLeftColor` then overrides. - _2026-08-04_ — **`Modal` (`vendor/ui/kit/Modal.tsx`) applies ZERO padding to its children — every caller must supply its own padded wrapper, or content sits flush against the modal edges** — unlike `Drawer` (`vendor/ui/kit/Drawer.tsx`), which bakes `padding: 24` into its own children wrapper, `Modal`'s content div is only `{ flex: 1, overflow: "auto" }`, no padding at all. `CreateAgentModal` gets this right (`<div style={s.body}>`, `padding: 24`, its own `styles.ts`) but `CreateSkillModal` (pre-existing, `app/skills/_components/CreateSkillModal/`) and a new Conventions-merge-to-skill modal both originally shipped without the wrapper and rendered edge-to-edge with a "broken" look (reported independently twice — once per modal). - _2026-08-08_ — **A scroll-target `useEffect` living on the destination card itself is not a stable enough lifecycle when its ancestor swaps subtrees mid-load** — `FileCard`'s original blast-radius "jump to file" implementation (`specs/0006-blast-radius-polish.md` §3c) scheduled `scrollIntoView` from `FileCard`'s own effect (deferred two `requestAnimationFrame`s to let `setOpen(true)` paint first). It never fired: `DiffTab` renders the flat `DiffViewer` fallback while `usePrSmartDiff` is loading, then swaps to `SmartDiffViewer` once it resolves — a full subtree replacement, not a re-render — so the target `FileCard` mounts, its effect schedules the deferred scroll, and the swap unmounts it (running the cleanup, cancelling the scheduled frames) before they fire; this repeated across the swap's several remounts (confirmed live: 4 "effect fired"→"cleanup" pairs within ~250ms, zero of the two rAF callbacks ever ran). - _2026-08-08_ — **`requestAnimationFrame` callbacks can silently never fire in this project's browser-automation testing tool** when its pane reports "not displayed, so the page is not compositing frames" (the same message `computer.screenshot` gives when the pane isn't visible) — confirmed by instrumenting a `useEffect`'s rAF chain: the effect body itself ran (logged), but neither the first nor a chained second `requestAnimationFrame` callback ever logged, even after several seconds. Rewriting the same wait as `setTimeout` fired immediately. Two implications: (1) prefer `setTimeout` over `requestAnimationFrame` for a "wait a tick then check the DOM" pattern in code that must also work headless/non-composited, not just for real foregrounded tabs; (2) **`Element.scrollIntoView({ behavior: "smooth" })` also silently never completes in a non-composited tab** (smooth-scroll is compositor-driven) — `{ behavior: "instant" }` applies immediately regardless. When verifying a `scrollIntoView`-based feature through this tool and the scroll position doesn't move even though your code logs that it called `scrollIntoView`, this is very likely why — don't conclude the feature is broken from that alone; substitute `instant` locally to confirm the target/position logic is correct, then trust `smooth` for real users (a real, foregrounded browser tab composites normally). Ship `smooth` when matching an existing convention (e.g. `FindingsPanel`'s own scroll-to-finding already uses it) — the non-completion is a property of this specific test harness, not of real browsers.
